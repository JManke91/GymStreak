# watchOS Localization (String Catalog)

## What it is
The watch target (`GymStreakWatch Watch App`) is localized in English (source) and German via a single String Catalog: `GymStreakWatch Watch App/Localizable.xcstrings`. Before 2026-07-11 the watch target had **no localization at all** — every string was a hardcoded English literal (while iOS localizes via legacy `en.lproj`/`de.lproj` `Localizable.strings` in `GymStreak/Resources/`).

## How it works
- The catalog is hand-authored JSON at the watch target root, next to `Assets.xcassets`. Because the project uses `PBXFileSystemSynchronizedRootGroup` (files auto-included by directory), no pbxproj edit was needed — the build compiles it into `en.lproj`/`de.lproj/Localizable.strings` in the app bundle automatically.
- Project `knownRegions` already contained `de` (from the iOS target), so no project-level change was needed.
- **Convention: the English text is the key.** SwiftUI `Text("...")`, `Label("...", ...)`, `.navigationTitle("...")`, `.accessibilityLabel("...")` literals resolve as `LocalizedStringKey` against the catalog with no code changes. `LocalizedStringResource` in App Intents (`Intents/GymStreakIntents.swift`) resolves the same way.
- Keys whose German equals the English ("Workout", "Pause" as a verb-label, "BPM", "kg") are **deliberately omitted** — a missing key falls back to the literal, which is already correct. Don't "fix" this by adding identical entries. ("Superset" is NOT such a key: German consistently uses "Supersatz", matching the iOS `superset.*` strings.)
- Plural-sensitive keys carry explicit plural variations for **both** en and de (en must be explicit there, otherwise "1 exercises"): `%lld exercises`, `%@, %lld exercises`, `%lld sets`, `You modified %lld sets. Update your routine template?`.

## Call sites that needed code changes (plain `String`, not auto-localized)
- `WatchWorkoutViewModel.swift` — `UNMutableNotificationContent` title/body (UserNotifications takes plain `String`) and the `?? "Workout"` summary fallback → wrapped in `String(localized:)`.
- `ExerciseListView.swift` — `ExerciseStatus.accessibilityLabel` switch literals → `String(localized:)`; the exercise-row accessibility label had English fragments (`", part of superset"`) buried inside one big interpolation (untranslatable as written) → restructured into `rowAccessibilityLabel` composing localized parts.
- `ActiveWorkoutView.swift` — hand-rolled English pluralization (`set\(count == 1 ? "" : "s")`) can't translate → replaced with the plural-variation key `You modified %lld sets. Update your routine template?`.
- `FullScreenSetEditorView.swift` / `WatchWorkoutSummaryView.swift` — `CompactValueEditor(label:unit:)` and `statRow(label:value:)` take `String` params, so literals at the call sites ("WEIGHT", "REPS", "reps", "Duration", "Sets", "Calories", "%lld cal") are wrapped in `String(localized:)` at the call site. The param types were intentionally left as `String` (no API churn).

## If the watch app renders entirely in English, check the scheme first
The shared scheme `GymStreak.xcodeproj/xcshareddata/xcschemes/GymStreakWatch Watch App.xcscheme` carried `language = "en"` / `region = "US"` on its `LaunchAction` from the day it was generated (commit `268f0d5`, the Fastlane screenshot work, 2026-02-07 — five months before the watch was localized at all). That is Xcode's **Run → Options → App Language / App Region**, and it injects `-AppleLanguages (en)` at launch, so *every* string rendered English on a watch whose own Language & Region is German. The iOS scheme never had it, which is why the phone looked correct and the watch did not.

Removed on 2026-09-01. Nothing depended on it: the screenshot lanes set their own languages (`fastlane/Snapfile`, `fastlane/Fastfile` `languages: ["en-US", "de-DE"]`), and watch UI tests read `UserDefaults.standard.array(forKey: "AppleLanguages")` themselves (`docs/watch-screenshots.md`).

**Order of diagnosis** when a watch string comes out English:
1. **Scheme launch language** — Product → Scheme → Edit Scheme → Run → Options → App Language must read *System Language*. This masks everything below it, and it is not visible anywhere in the app's code.
2. **Does the built bundle contain the German?** `ls "<built>.app"/*.lproj` and `plutil -extract "<key>" raw "<built>.app/de.lproj/Localizable.strings"`. A String Catalog entry left in state `new` is excluded from the build — see `.scratch/i18n-foundation/issues/01`.
3. **Is the string reaching the catalog at all?** A plain `String` API (notifications, `String` function params, computed `String` properties) is not auto-localized — see "Call sites that needed code changes" above.
4. Only then suspect the watch's own Language & Region setting. A watchOS app follows the *watch's* language; it does not inherit an iOS per-app language override.

## Muscle groups and equipment (localized at display time)
Muscle groups cross the sync wire as **raw English keys**, never as translated text: `WatchModels.swift` sends `routineExercise.exercise?.primaryMuscleGroup ?? "General"`, which is the same contract iOS uses internally (it stores English keys and localizes only when rendering, via `MuscleGroups.displayName(for:)` in `Domain/Models/MuscleGroups.swift`). Syncing already-localized names was considered and rejected: it would change the wire payload, freeze a translation into every cached routine on the watch, and break whenever the two devices disagree on language.

The watch therefore owns its own display-time table, `localizedWatchMuscleGroup(_:)` in `Extensions/WatchMuscleGroupLocalization.swift`, alongside `localizedWatchEquipment(_:)` for equipment raw values. Both are file-scope functions over the String Catalog, which holds the German for all 19 muscle keys plus `General` — the value iOS puts on the wire when an exercise has no primary muscle group, so it is a case of the table rather than a pass-through (iOS leaves it unmapped in `MuscleGroups.localizationKeys`, which is a latent English string on that side). Genuinely unknown values do pass through unchanged, so a future key added on iOS renders as its English name rather than as an empty row.

- **Every watch surface that shows a muscle group must call the helper.** They live in `Extensions/` rather than inside a view precisely because they were previously private to `WorkoutExerciseCatalogView.swift` and the routine-facing views never found them — the routine preview and the swap-exercise sheet printed "Upper Back" to a German user until 2026-08-31. Current call sites: `RoutineDetailView`, `ExerciseListView.subtitle(for:)`, `WorkoutExerciseCatalogView`, `WatchExerciseConfigurationView`.
- **The German wording is kept in sync with iOS's `muscle.*` strings** (`GymStreak/Resources/de.lproj/Localizable.strings`) — iOS is the reference, since those are the strings users have read since launch. Five values had drifted and were corrected on 2026-08-31: "Vordere/Seitliche/Hintere Schulter" (were plural "Schultern"), "Schräge Bauchmuskeln" (was "Seitliche Bauchmuskeln") and "Gesäßmuskel" (was "Gesäß").
- **`GymStreakWatchTests/WatchMuscleGroupLocalizationTests.swift`** guards the table: every key resolves, unknown values pass through, the key set equals iOS's `MuscleGroups.localizationKeys`, and every handled key has a String Catalog entry. The key-set assertion is why the enumerable `watchMuscleGroupKeys` exists next to the switch — add a key to one and the test fails until both sides agree. The catalog assertion goes through `Bundle.main` because under the tests' English locale a localized value is indistinguishable from a passed-through key; a missing entry is only visible against the bundle. Known residual gap: `watchMuscleGroupKeys` is a hand-maintained parallel list to the `switch`, so *deleting* a `case` while leaving the array intact still passes (the key returns unchanged, which is non-empty, and its catalog entry still exists). Single-sourcing it would mean replacing the `switch` with a `[String: LocalizedStringResource]` table; not done, because `String(localized:)` literals are the established extraction path in this target.

## Deliberate omissions
- **Dead code is not localized**: `WatchRoutinesViewModel.swift` (never instantiated) and the fully commented-out `SetNavigationBar.swift`. If either is revived, localize its strings then. (`ExerciseSetView.swift` and `RestTimerEditorSheet.swift` were on this list until they were deleted on 2026-07-25; `InlineSetEditorView.swift` and `ValueStepperView.swift` until 2026-08-28 — see below.) Same for `WatchWorkoutViewModel.errorMessage` — set in three places but never bound to any UI.
- Unit/abbreviation display inconsistencies ("CAL" in `MetricsView` vs "kCal" in `ExerciseListView`) were left as-is — display-design cleanup, not localization.
- **The "lbs" dead views are gone (2026-08-28).** `InlineSetEditorView.swift` and `ValueStepperView.swift` said `unit: "lbs"`, `step: 5` while every live surface was kilograms. The weight-unit feature (`docs/weight-unit-preference.md` §9a) made every watch weight read the unit synced from iPhone, so leaving them would have meant a *third* convention in a tree whose whole point is that there is one. Both were unreachable — `ValueStepperView`'s only caller was `InlineSetEditorView`, whose only caller was its own commented-out preview — so they were deleted rather than converted. Their `Comparable.clamped(to:)` extension has four live callers and moved to `Extensions/Comparable+Clamped.swift`.
- **Weight unit words are now localized**: `kg` / `lb` / `kilograms` / `pounds` (`Kilogramm` / `Pfund` in German), joined by `%@ %@`, all through `WatchWeightFormatting`. `%lld kg` and `%lld kilograms` were removed — nothing renders them any more.

## How to add a new watch string
Write the English literal in SwiftUI as usual, then add a key + `de` entry to `Localizable.xcstrings`. If the string reaches the user through a plain `String` API (notifications, computed `String` properties, `String` function params), wrap the literal in `String(localized:)` or it will silently stay English.
