# Guard the WatchConnectivity outbound-closure hazard with rules, not a restructured adapter

TestFlight build **1.1.10 (1001)** crashed a few seconds after every launch: a closure literal written inside `@MainActor final class WatchConnectivityManager` and handed to `WCSession.sendMessage`'s `errorHandler` inherited main-actor isolation, and Swift 6 inserted a *fatal* executor precondition instead of a diagnostic ([SE-0423]), so the process trapped the moment WatchConnectivity invoked it on its own operation queue (see `docs/swift6-concurrency.md` §4a). The three affected closures are fixed with `@Sendable`. This ADR records the separate question the crash raised — whether the adapter itself is structurally wrong — and the decision **not** to restructure it now, with the triggers that should reopen it.

## Considered Options

**Decompose the manager.** The obvious response to a 521-line iOS adapter (409 on the watch) is to split it, and CLAUDE.md's own 200–300 line guidance points that way. Rejected, because it prevents nothing: the decisive test is whether a candidate refactor would have stopped *this* crash, and splitting the class into smaller `@MainActor` types leaves the closure literal inheriting isolation identically. The size is also less meaningful than it looks — `Data/Sync/` already holds 25+ files with policy, state and orchestration extracted (`RoutineSyncAuthority`, `WatchSyncStateStore`, `WatchWorkoutInboxStore`, `WatchWorkoutIngestionCoordinator`, `WatchTemplateTransactionCoordinator`, `ExerciseCatalogSender`), so what remains is the WCSession adapter behind four transport protocols, not a god object that swallowed its collaborators. `docs/architecture-audit-2026-08.md` §5 separately reviewed both managers and returned **Hold**: WCSession delegate identity must be the launch-time instance, so their process-wide identity is genuine. That judgement is unaffected by this crash.

**Invert the adapter's default isolation.** This is the only shape that would have prevented the bug, and it names a real mismatch: the class is `@MainActor` while WatchConnectivity is inherently off-main. The inversion is measurably expensive — 10 `nonisolated` opt-outs and 9 `Task { @MainActor }` hops in the iOS file, 9 and 7 on the watch — to earn main-actor isolation for exactly **three** `@Published` booleans (`isReachable`, `isPaired`, `isWatchAppInstalled`). A `nonisolated` transport adapter with those three moved to a small `@MainActor` observable would make the safe thing the default. Rejected **for now**, not on principle: the hops it would add land precisely on the activation path whose ordering is load-bearing (challenge update before inbox drain), in code with a documented incident history — the 2026-08-01 head-of-line stall that needed a debugger to diagnose, a hoisting optimisation that was tried and reverted because it opened a mid-flight file-deletion window, and an SE-0431 ordering guarantee that `docs/watch-sync.md` marks as "deliberate and must not be swapped". The work is also doubled: the two managers are independent copies, with no symlink sharing between the targets, and the watch net is 34 tests against the iOS suite's 728.

**A typed `WCSession` seam** — an extension exposing `sendMessage(_:onError:)` with an `@escaping @Sendable` parameter, so the compiler rejects a main-actor literal. Rejected because it cannot remove the hazard it guards: the imported `sendMessage(_:replyHandler:errorHandler:)` keeps a different argument label and stays fully callable, so the wrapper only helps someone who already knew to reach for it — the same knowledge as knowing to type `@Sendable`. It trades "remember the attribute" for "remember the helper" while adding a parallel API over a system type, duplicated across both targets. Shadowing the real signature to force overload resolution was considered and rejected as too clever to survive maintenance.

**A SwiftLint custom rule**, the only genuinely mandatory guard available. Rejected on cost: the project has no `.swiftlint.yml`, no lint build phase and no CI lint step, so this means standing up lint infrastructure to carry one rule. A source-scanning unit test was rejected for the same reason under a different name — it introduces a pattern the codebase does not use, which CLAUDE.md warns against.

## Consequences

**The guard is documentation-only, and that is a deliberate accepted risk.** Recurrence is prevented by `CLAUDE.md` rule 4 (which now covers outbound completion handlers and makes "grep the SDK header for `NS_SWIFT_SENDABLE`" a checked step), `docs/swift6-concurrency.md` §4a, the §10 rule-5 checklist entry, a warning in `docs/watch-sync.md`, and a comment at each of the three call sites. All of it depends on being read. The trade is explicit: high blast radius on incident-scarred, ordering-sensitive, duplicated code, against a recurrence trigger — someone adding a fourth outbound closure — that is rare in a mature sync layer.

**The current surface is fully enumerated, which is what makes the trade acceptable.** `sendMessage` is the only WatchConnectivity API the app calls that takes a block; `transferUserInfo`, `transferFile`, `updateApplicationContext` and `activate` are block-free, and `sendMessageData` is unused. WatchConnectivity is also the only under-annotated framework in play — HealthKit (`HKObserverQuery.h:32`, `HKSampleQuery.h:57`) and Foundation (`NSTimer.h:38`) annotate their handlers `NS_SWIFT_SENDABLE`, so their closures are inferred nonisolated and carry no check. If that enumeration stops holding, the trade stops holding with it.

**A future isolation fix is provable rather than assumed.** `Yb` in a mangled symbol is `@Sendable`: `…Error_pYbcfU_` emits no executor check, `…Error_pcfU_` traps. §4a records both this and the `-O` A/B method, including the two traps that make a naive check useless — a hand-written Swift stub does not reproduce the bug at all, and a Debug build's `-enable-actor-data-race-checks` puts `reportUnexpectedExecutor` on every main-actor function and hides the signal.

**Reopen on any of three triggers**, at which point the isolation inversion is the option to plan — not decomposition, which the decisive test above already rules out. First, a fourth outbound WatchConnectivity closure appears (the typed seam also starts paying for itself at that point). Second, substantial new work lands in watch sync anyway, so the ordering paths are being touched and re-tested regardless and the marginal risk collapses. Third, the watch target's `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` decision is revisited for other reasons — that setting amplifies this hazard module-wide on the watch, so it is the same question wearing a different hat.

**The blast radius was reasoned about, not measured.** How many of those ~35 annotations would actually move, and which tests would need rewriting, is unestablished — this decision rests on reading the code and the incident history. Sizing that is the first step if a trigger fires, and it is the same caution `docs/architecture-audit-2026-08.md` §6 raises about its own P1/P2 claims.
