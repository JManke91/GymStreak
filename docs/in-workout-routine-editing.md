# In-Workout Routine Editing

## Purpose and current scope

In-workout routine editing lets a user change the exercise plan while an iOS workout is already running. An added exercise is configured with its number of sets, repetitions, weight, and rest time before it joins the live session. At workout completion, the existing **Update Routine Template** option controls whether exercise additions and removals become the plan for future workouts.

## iOS flow

`AddExerciseToWorkoutView` owns the picker navigation path:

1. Selecting an available library exercise pushes `ConfigureExerciseSetsView`.
2. Creating a custom exercise through `AddExerciseView` returns the new library exercise, then routes it through the same configuration step.
3. The configuration screen is the shared `ConfigureExerciseSetsView` (redesigned 2026-08-09 — see [routines-exercises-redesign.md](./routines-exercises-redesign.md)): exercise header, live summary, `RoutineSetsEditor`, rep-goal and rest-timer panels, and a sticky CTA. Its alternatives section is hidden for the live-workout flow because alternatives belong to routine-template configuration, and with no `destinationName` the CTA falls back to "add_to_workout.add".
4. On save, the finalized `[ExerciseSet]` scheme is passed to `WorkoutViewModel`, which translates it into `[WorkoutSet]` with `WorkoutSet(from:order:)`. That initializer copies each configured value into both planned and actual reps/weight.
5. `WorkoutViewModel.addExerciseToWorkout(exercise:configuredSets:targetRepMin:targetRepMax:)` attaches the workout exercise and every converted set to the current `WorkoutSession`, inserts them through `WorkoutSessionRepository`, and saves. The rep-range goal is copied onto the `WorkoutExercise`, so an exercise added mid-workout gets the same rep-progress badges and overload prompts as one that came from the routine.
6. Removing an exercise continues to affect only the live session until workout completion.
7. On completion, leaving **Update Routine Template** disabled preserves the original routine. Enabling it reconciles the routine against the completed session:
   - Existing slots are matched by `WorkoutExercise.routineExerciseId`. The exercise identifier/name fallback is retained only for historical workout edits, where routine membership is deliberately not reconciled.
   - Routine slots absent from the session are deleted and remaining slots are reordered.
   - Ad-hoc workout exercises are appended as new `RoutineExercise` slots with their configured sets, and the new slot identifier is written back to `WorkoutExercise.routineExerciseId` for stable history identity.
   - Existing exercises continue using the established set-count reconciliation, including performed values for completed sets.

Cancelling or navigating back from configuration does not add anything to the session. The save action remains disabled until at least one set exists.

## Architecture

The implementation uses existing domain models and repository boundaries across the established layers:

- `Presentation/Views/Workout/AddExerciseToWorkoutView.swift`: UUID-based picker navigation and forwarding of the configured set scheme.
- `Presentation/Views/Routines/RoutineExercisePickerView.swift`: shared `ConfigureExerciseSetsView`; configurable title, save label, and alternatives visibility keep one set-editing UI for both routine and workout flows.
- `Presentation/ViewModels/WorkoutViewModel.swift`: `ExerciseSet` to `WorkoutSet` translation, session mutation, slot-identity matching, and opt-in routine membership/set reconciliation.
- `Domain/Repositories/ExerciseRepository.swift`: identifier lookup resolves the library `Exercise` linked to a newly persisted routine slot.
- `Domain/Repositories/RoutineRepository.swift`: explicit `RoutineExercise` insertion complements the existing child mutation API.
- `Data/Repositories/SwiftDataExerciseRepository.swift` and `SwiftDataRoutineRepository.swift`: implement those persistence operations with `ModelContext` contained in Data.
- `App/ContentView.swift` and `Presentation/Views/Routines/RoutinesView.swift`: inject the already shared `ExerciseRepository` into `WorkoutViewModel`.
- `Domain/Models/Models.swift`: existing `WorkoutSet(from:order:)` performs the value-preserving conversion.

The original iOS editing slice added no persisted property or relationship: it reuses `RoutineExercise`, `ExerciseSet`, `Exercise`, and `WorkoutExercise.routineExerciseId`. Ticket 05 later added two optional `WorkoutSession` witness fields, described under Platform behavior below; those fields do require a CloudKit schema deployment.

When a routine slot is synthesized after the routine is already persisted, `WorkoutViewModel` follows SwiftData's relationship-ordering requirement: it inserts the unattached `RoutineExercise`, then links the persisted `Exercise` and `Routine`, then inserts and links each `ExerciseSet`. This avoids establishing relationships between models in different contexts.

## Platform behavior

### iOS

Supported in the active-workout add flow. Both existing library exercises and newly created custom exercises use the same configuration screen.

### watchOS

Ticket 06 adds live-session exercise membership editing on Apple Watch. `ActiveWorkoutView` retains the single workout-owned `NavigationStack`, but its path is now a homogeneous `[WorkoutRoute]` containing only UUID-backed routes: set editor, catalogue, and configuration. Every destination re-resolves its slot/catalogue selection, so removing a preceding exercise or refreshing the catalogue cannot make a stored array index point at the wrong model. The flow is pushed navigation—exercise list → synced catalogue → compact configuration—not a sheet.

`WorkoutExerciseCatalogView` explicitly distinguishes a never-synced catalogue from a valid empty library and a populated library. Active entries are disabled using identity in this order: library UUID, non-empty seed key, then normalized name only for a legacy active slot with neither known identity. A swap clears the prior seed key because the alternative wire model supplies a new UUID but no seed key; this prevents both the old and new library entries from appearing active. Muscle and equipment metadata is localized for English/German display and search. A configuration draft snapshots only the selected UUID/seed key and the four values; it does not retain a catalogue model. Commit re-resolves the latest item by UUID and then seed key. Failure leaves the live workout untouched.

The compact configuration defaults to one set, 10 reps, 0 kg, and 60 seconds rest. Sets, reps, and rest use pushed navigation-link pickers. Weight has a dedicated non-scrolling editor with one focused Digital Crown owner, touch ± controls, and VoiceOver adjustable actions. Commit atomically mints one slot UUID and distinct set UUIDs, copies planned values into actual values, makes the slot standalone, selects it, and returns to the exercise list. Back navigation discards the draft.

Removal uses a root-owned UUID confirmation so the dialog survives row/list changes. Completed work receives an explicit history-loss warning. The pure `WatchWorkoutStructuralReducer` performs idempotent removal, contiguous order normalization, cursor selection, two-member superset dissolution/three-member renumbering, zero-exercise handling, and UUID-keyed progress segments. Removing the final exercise deliberately leaves HealthKit running; the empty list still exposes Add Exercise and End Workout.

`WatchWorkoutStructuralBaseline` captures known and authoritative slot order at workout start, including pending-Watch-addition provenance. Session added/removed sets drive the current workout's dirty state; ordered outgoing arrays retain unconfirmed additions and pending-slot cancellation intent. `hasTemplateChanges` combines set and structural changes for manual and delayed auto-finish copy. Ticket 06 records this intent in active state; ticket 07 (see the ticket-07 summary below) carries it in the `CompletedWatchWorkout` payload and persists it through the watch→iOS transaction, so the two tickets are one release unit.

Structural input also extends the completion safety rules. Entering catalogue/configuration cancels the delayed auto-finish and suspends touch/hardware set mutations without pausing HealthKit. Add/remove cancel the delay again before mutation. Async set completion returns slot/set UUIDs and re-resolves them before applying; results are discarded after removal, input suspension, or terminal transition. The Action Button reliably reaches the guard and can play a failure haptic. Double Tap is disabled via `handGestureShortcut(..., isEnabled:)`; Apple does not deliver a callback when disabled/offscreen, so no mutation is guaranteed but a custom rejection haptic is hardware/system-delivery dependent.

**Ticket 05** turned "Save & Update Template" into an ordered, all-or-nothing **template transaction**. The durable unit is now a generic `TemplateTransactionEnvelope` (stable transaction id, sender epoch, per-routine sequence, optional workout correlation, extensible payload); the completed workout is ticket 05's first payload kind, not the queue identity. The same atomic replacement allocates identity/counter/anchor, and only the oldest pending transaction per routine may use either transport path. On iOS, `WatchTemplateTransactionCoordinator` gates on the sequence ledger and `WatchTemplateTransactionService` validates the complete set-only intent before committing history + template in one isolated save. Phased receipts repair partial receipt/index/ledger writes before acknowledging; unresolved ready receipts use a bounded recovery-marker set, so later authority challenges can restage current routines without repeating mutation or scanning indefinite receipt history. `RoutineSyncAuthority` persists generations before transport, never reuses an ambiguously sent generation, and hands over epochs instead of overflowing; the watch sender likewise rotates its epoch if a per-routine sequence is exhausted. On the watch, `WatchSyncStateStore` is the one atomic owner; failed ack/retirement/migration writes roll back in-memory state and cannot release a successor. `RoutineStore` remains only the published `effectiveRoutines()` projection, and terminal ack + correlated context can arrive in either order. Old iOS/watch builds retain the legacy workout/ack/context compatibility paths. Full protocol and verification details: see `docs/watch-sync.md` ("Template Transactions").

**Ticket 07** persists the watch's structural edits (ticket 06) through the same template transaction, making them durable routine changes when the user chooses **Save & Update Template**. It reuses ticket 05's transaction envelope, FIFO, receipts, executor, acknowledgment, and routine authority unchanged, and adds only membership intent.

*Wire contract.* `CompletedWatchWorkout` gains two optional, backward-decodable arrays — `addedRoutineExerciseIDs` (minted slot UUIDs added during the workout, in final exercise order) and `removedRoutineExerciseIDs` (known slot UUIDs removed, in workout-start baseline order) — and `CompletedWatchExercise` gains an optional `exerciseSeedKey`. Absence decodes to nil and the Data→Domain mapper normalizes the arrays to empty, so an old-watch/new-iOS payload is simply "no structural intent" and unknown keys stay decodable by an old iOS build. Both `WatchModels.swift` copies stay wire-identical. Deletion is never inferred from an exercise merely absent from a stale snapshot — only an explicit removal ID deletes, so stale omissions never become deletions. When `shouldUpdateTemplate == false` the arrays are historical metadata only and cannot mutate a routine.

*Pending provenance.* A Watch-added slot carries `isPendingWatchAddition == true` in the effective routine until iOS confirms it. Ticket 06's baseline excludes unresolved pending additions from the *authoritative* baseline but keeps them in the *known* baseline, so an unchanged pending slot is retransmitted and a later removal can still explicitly cancel it. Provenance clears only after ticket 05's versioned terminal acknowledgment and the correlated authoritative routine generation have both applied — at which point the transaction retires and the confirmed iOS slot (never pending) becomes the base.

*Idempotent watch merge.* `WatchRoutineTemplateFold` — the shared sync-state owner's optimistic overlay — now consumes the added/removed IDs in addition to set values: it deletes explicitly-removed slots (already-absent = no-op) with the same superset cleanup iOS performs (two or more remaining members keep the group UUID and renumber; a lone survivor is cleared), updates retained slots/sets, appends an addition only when its minted slot UUID is still absent (idempotent under duplicate finalization/transport), preserves unrelated slots added concurrently from iOS, and normalizes order. A pure set-only fold is byte-for-byte unchanged. `RoutineStore` stays a projection of `effectiveRoutines()` and never independently persists, queues, or merges.

*Exercise-library resolution (iOS).* The isolated transaction now also exposes an `ExerciseRepository` bound to the same context, so a resolved `Exercise` and the `RoutineExercise` it links commit in one save. Each addition resolves by payload UUID, then by the deterministic non-empty seed-key survivor (oldest `createdAt`, then smallest `id`, matching `DefaultContentSeeder`). It never falls back by name and never recreates a deleted `Exercise`. If neither resolves, denormalized history is saved but the entire template request is rejected and the optimistic Watch row is removed by the authoritative context.

*Authoritative iOS merge.* `WatchTemplateTransactionService` (with `applyStructural`) validates the whole request before mutating — final slot IDs unique, set IDs unique, added/removed arrays duplicate-free and disjoint, each added ID identifies exactly one final exercise, each removed ID absent from the final exercises, and every addition's library identity resolvable. ## Edge cases and deliberate omissions

- An exercise is not added until configuration is saved.
- At least one set is required.
- Configured set ordering is normalized during conversion.
- Planned and actual values start equal so the new exercise behaves like one copied from a routine template.
- Adding or removing an exercise does not mutate the routine until the user enables **Update Routine Template** at completion.
- Alternative exercises are not configured from the live-workout add flow.
- Exercise membership reconciliation runs only for active-workout completion. Updating an edited historical workout can still reconcile set values/counts, but it does not delete routine exercises added after that workout occurred.
- A new routine slot is created only when its `Exercise` still exists in the exercise library; the session history remains intact if the library lookup cannot resolve it.
- On watchOS, a catalogue selection that becomes stale is rejected without mutating the workout; UUID is resolved before seed key.
- On watchOS, removing the final exercise keeps the HealthKit workout active and requires an explicit End or Discard.
- On watchOS, structural edits affect the live session (ticket 06) and, when the user chooses **Save & Update Template**, become durable routine changes through the ticket-07 transaction. Declining the template update keeps them session/history-only.
- A Watch-added exercise persists into the routine only when its library `Exercise` still resolves (by UUID, then seed key); an unresolvable addition or any malformed structural intent rejects the whole template request while the workout history is still saved.
- Concurrent iOS routine edits win: only the exact slots the Watch explicitly added or removed are merged, and a Watch slot iOS deleted concurrently is never resurrected.
