# Watch ↔ iOS Routine Sync

## Overview
The GymStreak app syncs workout routine templates between iOS and watchOS using WatchConnectivity. iOS is the source of truth (SwiftData + CloudKit), while the watch maintains a lightweight local cache (an App Group state file owned by `WatchSyncStateStore`). Since ticket 03 of in-workout routine editing, the full **exercise catalogue** is additionally synced iOS → watch as tagged `transferFile` snapshots (see "Exercise Catalogue Sync" below) — independent of the routines `applicationContext` path.

## Architecture

### Data Flow

```
iOS (SwiftData + CloudKit)
  ↓ updateApplicationContext([WatchRoutine] as JSON)
Watch (WatchSyncStateStore: authority-checked base + optimistic fold;
     RoutineStore is a published projection of it)
  ↓ WatchWorkoutFinalizer: freeze one CompletedWatchWorkout into the durable
     outgoing queue (atomic App Group state file) BEFORE HealthKit, phase
     awaitingHealthKitMetadata → awaitingHealthKitFinish → transportEligible
  ↓ transport: sendMessage (fast path, when reachable) + transferUserInfo
     (guaranteed) — only for transportEligible entries; kept until iOS acks
  ↑ retried on activation / reachability / relaunch / background wake (never timers)
iOS (WatchWorkoutInboxStore: atomically persist exact bytes → serialized
     WatchWorkoutIngestionCoordinator drain → isolated single-save WorkoutSession
     → durable WorkoutIngestReceipt → remove inbox entry → workoutAck)
  ↓ acknowledgeWorkoutSaved (workoutAck) — watch retires the queue entry only now
```

Ticket 04 (in-workout routine editing) rebuilt this path so that **no** point in it treats a WatchConnectivity transfer callback or a `UserDefaults` write as an application-persistence boundary. Both the watch outgoing queue and the iOS receive inbox are serialized, throwing, atomically-replaced files; every completion runs one terminal finalization state machine with a frozen payload and stable identifiers; and only a semantic app-level acknowledgment retires state. See "Reliability Architecture" below.

### iOS Target
- **Persistence**: SwiftData `ModelContainer` with CloudKit (`iCloud.com.jmanke.gymstreak`)
- **Sync trigger**: `RoutinesViewModel.fetchRoutines()` calls `syncRoutinesToWatch()` after every fetch
- **Payload order is meaningful**: `syncRoutinesToWatch()` puts the `upNextRoutine` (next planned workout, else least-recently-trained — see `docs/workout-planning.md`) at index 0; the watch renders the first routine as its "Up Next" hero with a quick-start button (`RoutineListView`)
- **WC bootstrap**: `WatchConnectivityManager.shared` is bound as a `@StateObject` on `GymStreakApp` so the WCSession delegate is registered before any view appears (avoids cold-start activation race)
- **Receives workouts**: `WatchConnectivityManager.didReceiveUserInfo` AND `didReceiveMessage` (fast path) → validate routing envelope → **atomically persist exact bytes** to the durable inbox → trigger the serialized ingestion coordinator (`onWorkoutInboxUpdated`)
- **Receive inbox**: `WatchWorkoutInboxStore` — one atomically-replaced file per workout under `App Group/WatchWorkoutSync/Inbox/` (arrival-ordered filenames). Replaces the former `pendingReceivedWorkouts` `UserDefaults` blob (migrated on first init, order preserved). Malformed payloads are moved to `Quarantine/`; the last-good state is never touched.
- **Ingestion owner**: `WatchWorkoutIngestionCoordinator` — composition-root-owned (`AppDependencies`), **not** a ViewModel. Payloads are ingested before any view exists and mutation order is the inbox's arrival order, never task-scheduling order.

### watchOS Target
- **Persistence**: `WatchSyncStateStore` — one atomically-replaced App Group state file holding the routine base, the outgoing FIFO, the routine authority, and pending optimistic anchors. `RoutineStore` is a published projection over it and persists nothing itself (ticket 05; it previously kept its own `syncedRoutines` UserDefaults copy, migrated on first launch). The state file records when both legacy UserDefaults migrations have completed; the App Group defaults suite is then no longer opened on every watch launch.
- **Receives routines**: `WatchConnectivityManager.didReceiveApplicationContext` → `WatchSyncStateStore.applyRoutineContext(_:header:)`, which applies the routine authority's accept/reject rules before replacing the base
- **No SwiftData/CloudKit**: Watch uses lightweight Codable structs only
- **Sync-state owner**: `WatchSyncStateStore` — one atomically-replaced state file under `App Group/WorkoutSync/outgoing-queue.json`, owned by the watch `WatchConnectivityManager` (single WC lifecycle owner). Each entry carries a finalization **phase** so a relaunch never guesses whether a payload is safe to send. Replaces the former `pendingCompletedWorkouts` `UserDefaults` blob (migrated on first init as `transportEligible`, order preserved). Entries are retired **only** by an app-level `workoutAck`; transport is reconciled on Watch activation / reachability / foreground / background wake, after transient transfer failure, and on an explicit iPhone queue-drain request.

## Sync Methods

| Direction | Method | Behavior |
|-----------|--------|----------|
| iOS → Watch | `updateApplicationContext` (via `RoutineSyncAuthority`) | Coalesced (only latest delivered), guaranteed delivery. Carries `(routineSyncEpoch, routineSyncGeneration)` since ticket 05, so a delayed old context can never regress the watch. **Duplicate-suppressed** for ordinary syncs (2026-07-14): the send is skipped when the deterministically encoded payload equals the last one handed to WC this launch — CloudKit remote-change storms previously triggered dozens of identical re-syncs. The cache is in-memory (every launch resends once) and cleared on session deactivation and on a newly installed/switched watch app, so a new watch is never starved. (A dead, uncalled `sendRoutinesIfReachable` sendMessage fallback that would have bypassed the suppression was removed.) |
| Watch → iOS (fast) | `sendMessage` | Real-time, requires reachability — fired alongside transferUserInfo for immediate UI updates. Only for `transportEligible` queue entries |
| Watch → iOS (guaranteed) | `transferUserInfo` | System-managed background transfer that does not require `isReachable`. `didFinish` success ≠ app persistence, so the watch keeps its queue entry until iOS sends an app-level ack. Every reconciliation suppresses an identical semantic id already in `outstandingUserInfoTransfers`; an explicitly failed transfer is no longer outstanding and is eligible for a later retry |
| iOS → Watch (queue drain) | `requestWorkoutQueueDrain` → reachable `sendMessage` **or** unreachable `transferUserInfo` | Idempotent wake-up request sent only after WCSession is activated, paired, and the Watch app is installed. Reachable sessions use only the immediate message; unreachable sessions keep at most one durable request. A message error falls back to one durable request. Receipt performs ordinary Watch queue reconciliation and never bypasses outstanding-transfer suppression |
| iOS → Watch (save ack) | `acknowledgeWorkoutSaved` → `sendMessage` + `transferUserInfo` | Confirms the WorkoutSession is durably committed (or already present via a receipt); the watch retires the workout from its outgoing queue only on this ack. Clears **no-template** workouts only |
| iOS → Watch (template ack) | `acknowledgeTemplateTransaction` → `sendMessage` + `transferUserInfo` | Versioned terminal acknowledgment for a template transaction (outcome + staged routine generation). Sent only after the authoritative routine snapshot is staged; the watch holds it until that generation has applied locally |

## Reliability Architecture (Watch → iOS Workout Sync)

This path historically had silent-loss failure modes (workouts saved to HealthKit but never appearing in iOS history). **Ticket 04** (in-workout routine editing) rebuilt it around one principle: **transport delivery and `UserDefaults` writes are never treated as application-persistence boundaries.** Both queues are serialized, throwing, atomically-replaced files; every completion runs one terminal finalization state machine; and only a semantic acknowledgment retires state.

> **This closes the *durability* window, and — since the history/template split — the liveness window that mattered.** Ticket 04 guarantees a finalized payload is never *destroyed*; it does not by itself guarantee it is ever *sent*. Until the split, a workout carrying template intent travelled as one transaction gated on the per-routine FIFO head, so anything that permanently prevented the head from being acknowledged permanently prevented every later workout for that routine from being transmitted at all — with the payload intact on the watch the whole time. That is not hypothetical, it shipped (2026-08-01 incident). **Workout history now travels as its own ungated entry** (ADR 0001, "Split template intent" below), so a stalled head can cost only template updates for one routine.

### Terminal finalization state machine (watch)

`WatchWorkoutFinalizer` runs one sequence shared by manual End, auto-finish, and (later) ticket 06 structural editing. `WatchWorkoutViewModel` freezes the workout the moment finalization begins (`isWorkoutFrozen`) — every set mutator, swap, rest-time edit, Action-Button/Double-Tap input, and `discardWorkout` is rejected while frozen, and the delayed auto-finish task is revalidated/cancellable so a manual End racing it can't fire a second attempt.

1. **Durable freeze before any irreversible transition.** The finalizer builds exactly one `CompletedWatchWorkout` — one final end time, stable workout UUID (`pendingCompletedWorkoutId`), preallocated stable HealthKit external UUID (`pendingHealthKitWorkoutId`), stable ordered exercise/set ids — and `enqueue`s it into `WatchSyncStateStore` at phase `awaitingHealthKitMetadata`. The enqueue write is the persistence boundary: **if it throws, nothing external has happened and the user returns to editing.** After it succeeds the workout can no longer be discarded. When the workout requests a template update, that single write commits **two** entries (the split below); the finalizer receives the history one, which is the half that carries the frozen bytes and the HealthKit phases.
2. **Required external-UUID metadata.** `WatchHealthKitManager.endCollectionAndAddMetadata(externalId:)` ends live collection and stamps `HKMetadataKeyExternalUUID` (+ `RoutineId`/brand name). GymStreak uses that UUID for cross-device correlation; **HealthKit permits duplicate external-UUID values and does not dedupe on them**, so a metadata failure *throws* — it is never swallowed into a transportable state. On success the queue advances to `awaitingHealthKitFinish`.
3. **Finish the same workout/builder.** `finishWorkout()` finishes the identical builder; on success the queue advances to `transportEligible`. A finish failure keeps session/builder alive so a retry finishes the *same* workout.
4. **Transport is separate.** Only now is transport triggered. Retries re-enter `finalize` with the same workout id: the frozen queue entry's phase decides which steps still run — **payloads are never reconstructed and completed HealthKit steps never repeat** (`hasEndedCollection` guards the collection end). `pendingCompletedWorkoutId`/`pendingHealthKitWorkoutId` persist across a retried end so a HealthKit failure re-uses the same identity.

Because the payload is frozen *before* the HealthKit save, the old loss window (HK save first, then enqueue → crash between them stranded a workout in Apple Health with no payload anywhere) is closed structurally, not by ordering luck.

**Summary UX must not wait on HealthKit (regression fixed 2026-07-21).** The finalizer fires an `onFrozen` callback the instant the durable enqueue succeeds — before any HealthKit call. `WatchWorkoutViewModel.endWorkout` shows the post-workout summary (and clears `isWorkoutActive`) from `onFrozen`, because once enqueued the workout *will* reach iOS regardless of the HealthKit outcome (see the recovery ladder below, which makes that promise structural). Do **not** re-gate the summary on the finalizer's final outcome: an interim version did exactly that, so on the last set (auto-finish → `endWorkout`) the workout screen stayed frozen (`isWorkoutFrozen` blocks all input) for the whole `endCollection → addMetadata → finishWorkout` await, and the stuck UI made the Action Button's Complete-Set App Intent time out ("Satz abschließen … ist fehlgeschlagen"). A HealthKit metadata/finish failure is therefore non-fatal to the UX — the summary is already up; only `.notEnqueued` (nothing external happened) returns the user to editing. `isEnding` is also reset in `startWorkout`/`resetState` so a slow or hung HealthKit finish can never leave a subsequent workout frozen.

**HealthKit-failure recovery ladder.** A `.healthKitFailed` outcome leaves the entry in an `awaitingHealthKit*` phase, which transport skips — without recovery the workout would be stranded despite the summary the user saw. Two bounded triggers close that gap:

1. **In-process retry on summary dismissal.** `WatchWorkoutViewModel.dismissSummary` re-enters `finalize` for an entry still in a HealthKit phase (no `onFrozen`; reentrance rejected by the finalizer), while the bound session/builder still exist — success also preserves the Apple Health record.
2. **Promotion (backstop).** `WatchSyncStateStore.promoteInterruptedFinalizations()` promotes entries a previous process left in a HealthKit phase straight to `transportEligible`. This can never create a HealthKit-side duplicate: `finishWorkout()` is the only step that saves the `HKWorkout` and metadata precedes it, so an interrupted finalization either produced no `HKWorkout` at all (its Apple Health record is lost — GymStreak history is primary) or produced a complete, externally-identified one (crash between finish and the phase write), which iOS ingestion handles idempotently. **Ticket 08 moved this off the eager `WatchConnectivityManager.init` path** (a blind promotion there would abandon a still-running session and could block the next workout): it now runs as the recovery coordinator's sweep for non-primary entries and as a cold-background-wake backstop in `handleWatchConnectivityBackgroundWake()`.
3. **Live-session recovery (ticket 08).** On a foreground relaunch, `WatchWorkoutRecoveryCoordinator` reconnects a still-active `HKWorkoutSession` via `recoverActiveWorkoutSession` and either resumes the live workout (from a durable app checkpoint) or finishes the interrupted finalization on the real session. See **`docs/watch-workout-recovery.md`** for the full crash-boundary decision table, the checkpoint format, supported-OS behavior, deliberately-unrecoverable cases, and the pending paired-hardware matrix.

**Finalization is bound to its session/builder pair.** `WatchHealthKitManager` captures the (session, builder, routine metadata) it starts finalizing, keyed by the external UUID (`BoundFinalization`), and every finalization step operates on that binding — never on the live `workoutSession`/`workoutBuilder`. Without this, a retried or still-running finalization after `startWorkout` replaced the live pair would end/finish the *new* workout's session. Finishing tears down live-workout state only when it still belongs to the finished workout; a binding abandoned for a different workout is discarded when the next finalization begins.

**Guarding the active workout against accidental dismissal.** A modally-presented `NavigationStack` auto-fills its leading toolbar slot with a system close ("X") that `.interactiveDismissDisabled()` does not suppress (that modifier only governs drag-to-dismiss, absent on watchOS). Left as the default it dismissed the workout cover directly, bypassing the End-Workout confirmation and leaving the `HKWorkoutSession` running (the user could then start a second workout). `ActiveWorkoutView` now claims that slot with its own `.cancellationAction` button routed through the existing Save / Discard / Continue dialog, and `RoutineListView` adds a `fullScreenCover(onDismiss:)` teardown safety net (never `.onDisappear`, which can fire on wrist-down and would wrongly kill a live workout) that discards the session if the cover is ever closed while a workout is still live and unfinalized.

**Deferring visible-state teardown to `onDismiss` (empty-screen flash fix).** `ActiveWorkoutView`'s body renders the summary when `workoutSummary != nil`, otherwise the workout tabs (whose exercise list shows "no exercises" when `exercises` is empty). Originally the Discard button called `viewModel.discardWorkout()` and the summary's Done button called `viewModel.dismissSummary()` *before* `dismiss()`; both synchronously clear the view model's `@Published` state (`resetState()` sets `exercises = []`, `dismissSummary` also nils `workoutSummary`). Because the state cleared while the cover was still animating away, SwiftUI re-rendered the now-empty active-workout screen for the duration of the dismiss animation — a visible flash of the "no exercises" screen. Fix: both buttons now call `dismiss()` only, and *all* visible-state teardown is deferred to `RoutineListView`'s `fullScreenCover(onDismiss:)`, which dispatches once the cover is off screen — `workoutSummary != nil → dismissSummary()`, else `isWorkoutActive → discardWorkout()`. The explicit Discard button and an accidental cover dismissal both converge on the same `discardWorkout()` branch. `discardWorkout()`'s `isWorkoutFrozen` guard still protects a mid-finalization workout; HealthKit teardown simply moves ~one dismiss-animation later, which is inconsequential.

### Transport and acknowledgment (watch)

`WatchWorkoutTransportCoordinator` moves only `transportEligible` entries; it never constructs workout state or touches HealthKit. When iOS is reachable it sends the immediate `sendMessage` fast path; it also enqueues the identical frozen bytes with `transferUserInfo` unless that semantic transaction/workout ID is already present in `outstandingUserInfoTransfers`. Both paths converge through ID-based dedupe on iOS. Every lifecycle and receiver-driven reconciliation applies the same outstanding-transfer suppression. Apple defines this collection as transfers that have not been cancelled, failed, or received, so treating one as “stale” and force-enqueueing behind it is forbidden. If a transfer explicitly fails it leaves the outstanding set; the retained app-owned entry then becomes eligible on the bounded retry or next lifecycle/request trigger. The queue-drain request is only a wake-up signal, never authority to bypass sender-queue truth. The app-level ack remains the only retirement signal.

This follows Apple's transport split: [`transferUserInfo(_:)`](https://developer.apple.com/documentation/watchconnectivity/wcsession/transferuserinfo(_:)) is the background-transfer API, while [`isReachable`](https://developer.apple.com/documentation/watchconnectivity/wcsession/isreachable) describes only whether an immediate message can be sent. `outstandingUserInfoTransfers` is sender-side queue visibility, not an application acknowledgment. After an iPhone reboot, WatchConnectivity also reports that [the iOS device may need its first unlock](https://developer.apple.com/documentation/watchconnectivity/wcsession/iosdeviceneedsunlockafterrebootforreachability); the hardware procedure must therefore power on **and unlock** the phone before judging recovery.

- `session(_:didFinish:error:)` is **transport diagnostics only**. Success never retires a queue entry: it is not proof that GymStreak persisted the workout. Errors are classified: `payloadTooLarge` / `payloadUnsupportedTypes` / `invalidParameter` (and local encode failures) are **terminal for those exact bytes** → the entry is `quarantined` (kept for diagnostics, never hot-looped); every other error keeps the entry and schedules one coalesced five-second retry in addition to lifecycle recovery.
- Retirement happens **only** on the app-level `workoutAck`: `handleIncoming` delegates acknowledgment to `WatchSyncStateStore`, which retires the matching queue entry only when its protocol phase permits. iOS re-acks every duplicate and the watch retries on every activation/reachability/relaunch/background-wake, so a lost ack or transfer self-heals.

### Head-of-line liveness (2026-08-01 incident — root cause and fix)

> **Structural resolution.** Everything below repairs the ways the head could stall; the split described under "Split template intent" removes the consequence. **Workout history is no longer gated on anything** — it is enqueued as its own ungated entry and retires on the plain acknowledgment. A permanently unretired head now withholds later *template updates* for that one routine and never a workout.

**Symptom.** A standalone Watch workout (49 min, "Push") was saved to Apple Health but never reached iOS. The History tab offered it as an orphaned-workout recovery candidate. The payload was intact on the watch the entire time and had **never been handed to WatchConnectivity once**.

**Chain.** The workout used *Save & Update Template* and the user had accepted two mid-workout progressive-overload suggestions, so the routine's FIFO held three transactions: overload seq 3, overload seq 4, the completed workout seq 5. iOS received and correctly *committed* seq 3 (the routine really did move to 30 kg @4) — then could not acknowledge it, because `stageContextAndAcknowledge` → `RoutineSyncAuthority.send(payload:)` found no watch challenge and withheld the authoritative snapshot. The receipt parked at `committedAwaitingContext` forever, so seq 3 was never retired on the watch, so `transportEligibleEntries()` never released seq 4 or seq 5.

**Root cause — callback ordering, not just missing state.** `RoutineSyncAuthority.challenge` was **process-local and populated at exactly one point**: `activationDidCompleteWith` reading `session.receivedApplicationContext`. In that same callback, the inbox drain (`onWorkoutInboxUpdated`) ran **before** the challenge was parsed. And it could not have succeeded any earlier either — `canSyncRoutines` refuses to send until `activationState == .activated`, so the `AppDependencies.init` launch drain can never stage a snapshot no matter what the authority knows. Activation was therefore the first moment staging was possible, and the drain was running one statement too soon, every launch. The watch's challenge was published correctly and sat in `WCSession.receivedApplicationContext` the whole time.

**Fix, in order of load-bearingness:**

1. **Ordering (the actual repair).** `activationDidCompleteWith` now updates the challenge *before* draining the inbox. This is the only change that fixes the observed case on its own.
2. **`WorkoutIngestReceiptStore.unresolvedTemplateReceipts()`** now also returns `committedAwaitingContext` receipts (and `record` writes their recovery marker), so `recoverReadyReceipts()` retries them. Previously such a receipt was retried **only** by an inbox drain — removing its inbox entry left it permanently unacknowledgeable. This is what repairs receipts already stranded by the bug.
3. **Defence in depth.** `RoutineSyncAuthorityState.lastChallenge` persists the last challenge, and `RoutineSyncAuthority.resolvedChallenge()` falls back to `RoutineContextTransporting.receivedWatchContext`. Neither helps before activation (see `canSyncRoutines`); they cover the paths where the challenge arrives only via `didReceiveApplicationContext`, or where the cached context is momentarily empty. A stale persisted challenge is safe: the watch re-validates every context against its own retired-epoch / target-instance / `fromEpoch` / nonce rules, so the worst case is a rejected context or a proposal bound to a dead tuple — cleared by `updateChallenge` when the real challenge arrives — never a wrong apply.

**Also fixed (latent, not part of this incident):** a `quarantined` entry could hold the per-routine FIFO head. Quarantine is terminal — the bytes can never transport and no acknowledgment will ever retire them — so it blocked every later transaction for that routine on the watch. `isHeadTransaction`, `retireSatisfiedAcknowledgments` and `effectiveRoutines()` now all apply the same terminal-entry rule, and `quarantine` fires `onTransportEligibilityChanged` so the released successor reconciles immediately.

> **Residual, deliberately not fixed here:** releasing the successor moves the block from the watch to iOS rather than removing it. The watch consumed sequence *N* for the quarantined entry, so `WatchTemplateTransactionCoordinator` sees *N+1* as `sequence > expected` and buffers it in the durable inbox indefinitely — but only when a ledger already exists for that `(senderEpoch, routineID)`; if the quarantined transaction was the first sequenced one for the pair, `nextExpectedSequence` returns nil and the successor establishes the ledger and ingests normally.
>
> This is a **trade, not a strict improvement**. Better: the payload is durably on the phone instead of stranded on the watch, so nothing is lost and it converges the instant the gap is closed. Worse: `WorkoutRecoveryReconciler` postpones on `isBufferedOrDraining` with **no time bound**, so a permanently buffered entry silently suppresses the orphaned-workout recovery banner — the very escape hatch that surfaced this incident to the user. Keeping the head-skip is still correct (reverting it reinstates an unbounded watch-side deadlock in which the successor is never even transmitted), but closing the gap properly needs one of: an explicit abandoned-sequence marker so the iOS ledger can advance, or a bounded `inboxInFlight` postpone that offers recovery once an entry has been buffered out-of-order beyond some age.
>
> **Downgraded by the split.** Since history and template intent are separate entries, a quarantined transaction can only ever leave a sequence hole in the *template* lane of one routine — the buffered successor is a template update, not a workout, and no history is implicated. That turns this from potential data loss into a degraded feature, which is why it stays open for field evidence rather than being fixed speculatively (ADR 0001, "The quarantine sequence-ledger gap"). "Fail forward on quarantine" is also no longer one of the candidate fixes: the workout it would have rescued now travels on its own regardless.

### Observability (`WatchSyncDiagnostics`)

The incident needed a debugger and two `po` calls to diagnose, for a structural reason: the whole delivery path used `print()`, which writes to stderr and is **invisible in Console.app for a device build**. A support log could not have shown any of it.

`WatchSyncDiagnostics` (identical copy in both targets, `subsystem: com.shotat24fps.GymStreak`, `category: WatchSync`) replaces every `print` on the watch → iOS workout delivery path: the durable queue (`WatchSyncStateStore`), transport (`WatchWorkoutTransportCoordinator`, both `WatchConnectivityManager`s), the receive inbox and ingestion (`WatchWorkoutInboxStore`, `WatchWorkoutIngestionCoordinator`, `WatchTemplateTransactionCoordinator` and its progressive-overload kind, `WorkoutIngestReceiptStore`), and the routine authority the acknowledgment depends on (`RoutineSyncAuthority`). Catalogue sync, CloudKit and checkpoint stores are deliberately out of scope — separate subsystems, not implicated.

Conventions:

- **Identifiers are shortened, one-way, launch-stable tokens** — never raw UUIDs, and never exercise names, weights, reps or payload bytes. The algorithm is shared with `WorkoutRecoveryDiagnostics` (which now delegates to it), so a token means the same object under either category and support logs correlate across the seam. Callers own shortening anything they interpolate; that is the privacy boundary.
- **Levels carry meaning.** `info` = normal progress. `notice` = handled by the protocol (suppressed duplicate, retained payload, buffered successor). `error` = failed but durable state stays replayable. `fault` = terminal or liveness-threatening — data that can no longer converge on its own, or work stalled with no bounded escape.
- The three conditions that produced this incident are all `fault`: the authority withholding a context for want of a challenge, a transaction parking at `committedAwaitingContext` unacknowledged, and a per-routine head unretired past `stalledHeadFaultMinutes` (2 h) with entries withheld behind it. Each message states the consequence, not just the event.

Unlike `WorkoutRecoveryDiagnostics`' one-typed-method-per-event shape, this is a leveled message seam — the call sites are numerous and their messages already meaningful, so a 1:1 conversion kept them readable and reviewable.

**Still missing:** neither app *surfaces* "the watch is holding N undelivered workouts" to the user. The iOS side has the orphaned-workout banner, but that fires from HealthKit discovery, not from watch queue state, and it stays silent while an entry is merely withheld. A watch-side pending count with a manual retry remains unbuilt.

**Resolved — history is no longer gated on template ordering.** A completed workout carries two things with very different value and very different constraints: *history* (must never be lost, order-independent — `processNoTemplate` ingests it unordered) and *template intent* (ordered, mergeable, losable). They used to be fused into one transaction, so history inherited the template's ordering and acknowledgment fragility. The fixes above removed the known ways the head can stall permanently; the structural fix landed with `docs/adr/0001-split-workout-history-from-template-intent.md` — iOS accepts the split form and the watch emits it, so a stalled template acknowledgment now costs a template update and never a workout. See "Split template intent" below.

### Durable receive inbox (iOS)

`WatchConnectivityManager.handleIncomingPayload` (both `didReceiveUserInfo` and the `sendMessage` fast path) validates only the routing envelope, then **atomically persists the exact payload bytes** to `WatchWorkoutInboxStore` BEFORE any ingestion, notification, or ack. If that write fails, no ack is sent and the watch's durable queue redelivers. WatchConnectivity receive callbacks do not establish app persistence — this is GymStreak's crash-safety policy, not an Apple dictionary-lifetime requirement. The inbox is drained serially by the coordinator on receipt, launch, and WCSession activation; independent unstructured tasks never determine mutation order.

### Isolated no-template ingestion + durable receipts (iOS)

`WatchWorkoutIngestionCoordinator` (composition root) drains the inbox oldest-first. Per entry:

- **A durable receipt already exists** → acknowledgment-only, no re-ingestion. Receipts survive history deletion, so a session the user deleted is never resurrected by a stale redelivery.
- **No-template workout** → a fresh `ModelContext` (`SwiftDataWorkoutHistoryTransaction`, `autosaveEnabled = false`) materializes the complete denormalized history graph (stable workout/HK/exercise/set ids) and `save()`s **exactly once**. Unrelated dirty main-context work is *deferred*, never saved or rolled back by ingestion. On save failure the isolated context is rolled back, both durable queues stay intact, and nothing is acked. On success a terminal `WorkoutIngestReceipt` (phase `readyToAcknowledgeNotRequested`) is persisted **before** the inbox entry is removed or the workout acked. If the receipt write fails the entry stays replayable and nothing is acked; the next drain dedupes against the committed session, persists the receipt, then acks (this also covers migrated "history exists but receipt absent" cases).
- **Template transaction** → delegated to `WatchTemplateTransactionCoordinator` (ticket 05): sequence-gated, committed in the same kind of isolated single-save context, then phased receipt → authoritative routine snapshot → versioned terminal acknowledgment. See "Template Transactions" below.

**Missing routine → no placeholder.** `WorkoutSession.init(routine:)` now takes `Routine?`. When the routine was deleted since the watch cached it, ingestion produces denormalized history with `routine == nil` (the denormalized `routineName` drives display) — it never inserts a placeholder `Routine`, which would resurrect the deleted template and re-sync it back to the watch.

**Placeholder replacement (critical, unchanged).** A match by `healthKitWorkoutId` under a *different* session `id` uniquely identifies a session the recovery banner reconstructed from HealthKit (template values guessed as actuals) — real ingests always preserve the watch-generated id, and a watch-generated HK external UUID can never collide with an iPhone-recorded session's. In that case the ingest **deletes the placeholder and inserts the real payload** instead of skipping. This stays idempotent: a later duplicate is answered acknowledgment-only.

**Receipt retention & performance.** Because stale WatchConnectivity delivery has no published lifetime bound, exact-dedup receipts are retained **indefinitely** — they are deliberately NOT pruned without a separately proven safe compaction scheme. To keep indefinite retention from becoming an ever-growing monolithic-rewrite bottleneck, `WorkoutIngestReceiptStore` uses one tiny file per receipt under `WatchWorkoutSync/Receipts/` — `<workoutId>.json` for a no-template workout, and since ticket 05 `tx-<senderEpoch>-<routine>-<sequence>.json` for a template transaction, plus an `Index/` correlation entry and a `Sequences/` ledger with O(1) record and lookup. A separate `ReadyRecovery/` marker exists only while a terminal receipt still needs routine-authority recovery; once the watch proves the correlated generation applied, the marker is removed while the receipt remains for duplicate lookup. Authority changes therefore inspect unresolved work rather than scanning indefinite receipt history. Recorded budgets (see Tests below): 1000 receipt writes < 10 s, 1000 lookups < 5 s; 150 outgoing enqueue+advance cycles against the growing state file < 10 s. (Budgets are generous to avoid CI flakiness; they exist to catch accidental O(n²) regressions, not to benchmark hardware.)

### HealthKit incremental discovery + conservative recovery (iOS, ticket 09 of in-workout routine editing)

Ticket 09 replaced the old moving 30-day full-store poll (`HealthKitWorkoutReconciler`, deleted) with an **incremental, background-aware discovery pipeline** feeding a **durable recovery ledger** and a **pure conservative reconciler**. The engine is `WorkoutRecoveryCoordinator`, owned app-lifetime by `AppDependencies` (not a ViewModel) so discovery runs before any view exists. It wires:

```
HKObserverQuery / launch / foreground  →  anchored incremental drain  →  ledger
  (apply deletions + discoveries idempotently)  →  persist anchor AFTER ledger commit
  →  reconcile against live sync facts  →  publish user-confirmable candidates
```

**Incremental discovery (`HealthKitAnchoredWorkoutDrain` + `HealthKitWorkoutAnchorStore`).** A serialized `HKAnchoredObjectQueryDescriptor.result(for:)` over `HKObjectType.workoutType()` drains all pages in one call, returning added samples, `HKDeletedObject`s, and a new `HKQueryAnchor`. The opaque anchor is persisted (`NSKeyedArchiver`, `HKQueryAnchor` is `NSSecureCoding`) in the App Group so discovery is incremental across observer wake-ups and relaunches. **Anchor↔predicate stability is a hard rule:** the anchor encodes "everything already seen for *this exact predicate*", so it is paired with a **fixed** lower-bound date (established once, 30 days before first run, then frozen), never a moving `now − 30 days` window — a shifting predicate against a stored anchor produces undefined diffs. The anchor is committed **only after** the ledger writes it produced are durable, so a crash between drain and persist replays the same changes idempotently instead of skipping them. A corrupt stored anchor decodes to nil and re-bootstraps through the same idempotent path. Added workouts are filtered to the GymStreak bundle prefix (`com.shotat24fps.GymStreak`) carrying `HKMetadataKeyExternalUUID`; routine name/id come from `RoutineName`/`HKMetadataKeyWorkoutBrandName`/`RoutineId` metadata.

**Deletions and the correlation table.** `HKDeletedObject` exposes only the HealthKit *object* UUID — the system does **not** preserve `HKMetadataKeyExternalUUID` (or any custom metadata) on deletion. The ledger therefore doubles as the persisted `HKObject.uuid → externalUUID` correlation table: each entry records the set of HealthKit object UUIDs seen for its external UUID, and a deletion is mapped back to a candidate by scanning those sets. HealthKit permits several samples to share one external UUID; a second, different object UUID is unioned in and flagged as a **conflict** (`hasExternalUUIDConflict`), which the reconciler diagnoses and refuses to reconstruct rather than risk duplicate history.

**Observer + background delivery (`HealthKitWorkoutObserver`).** One long-lived `HKObserverQuery` for `workoutType()` is registered at launch, and `enableBackgroundDelivery(for:frequency:.immediate)` requests wake-ups. The observer is only a wake/change signal — never the workout-completion clock (watch→iPhone Health sync is system-controlled and non-real-time; `.immediate` is a *maximum* request under system policy, not a latency guarantee). Its handler runs the bounded drain and then calls the HealthKit completion handler **exactly once** (success or failure) so the background-delivery budget is released; on failure the anchor is left unchanged and the next notification or foreground launch retries. Requires the **`com.apple.developer.healthkit.background-delivery`** entitlement (added to `GymStreak.entitlements`; separate from the existing `healthkit`/`.access` keys — no `UIBackgroundModes` entry is needed for HealthKit wake-ups). **Background observer delivery is unavailable on the Simulator** — the launch/foreground drain is the fallback there and wherever background delivery is delayed or disabled.

**Recovery ledger (`WorkoutRecoveryLedgerStore`, `WorkoutRecoveryLedgerEntry`).** Durable App-Group JSON, one tiny file per external UUID (the same append-only, O(1)-lookup representation as `WorkoutIngestReceiptStore`, and for the same reason — stale WatchConnectivity delivery has no published lifetime bound). Kept strictly separate from authoritative routine/template state; it never mutates a routine. Each entry holds the candidate facts needed to build a placeholder, the HealthKit object-UUID set, discovery/deletion/reconcile timestamps, a last-error string, a lifecycle `state` (`provisional → resolvedByHistory | placeholderSaved → placeholderReplaced | tombstoned`), and (for a saved placeholder) the placeholder's session id for replacement detection.

**Conservative reconciler (`WorkoutRecoveryReconciler`, pure).** For each candidate it produces `resolve | postpone(reason) | offerRecovery | conflict` from live facts, in strict order:
1. Rich history **or** a terminal ingest receipt for the external UUID → `resolve` (no reconstruction). History comes from `WorkoutHistoryCorrelationProviding.healthKitWorkoutIDs()` (fresh context on the shared container — never a ViewModel cache). The receipt is consulted via the new external-UUID index on `WorkoutIngestReceiptStore`, so a workout that was already ingested and then **deleted** by the user is never re-offered (which would resurrect deleted history).
2. Duplicate external UUID → `conflict` (diagnosed, never reconstructed).
3. The exact payload is buffered/inboxed locally (`WatchConnectivityManager.pendingWorkouts()` by `healthKitWorkoutId`) → `postpone(.inboxInFlight)`.
4. `WatchConnectivityManager.mayHaveUndeliveredContent` (`hasContentPending == true`, or session not activated) → `postpone(.watchConnectivityPending)`. **`hasContentPending` is positive-only:** `true` is a reason to wait; `false` proves nothing (it reports only this device's local receive queue, never the watch's send queue, immediate messages, or HealthKit sync) and is **never** treated as proof that delivery is finished.
5. Still within the 60 s grace period since discovery → `postpone(.withinGracePeriod)`. The grace period is **UX policy, not a correctness boundary** — no Apple API supplies a safe "payload will never arrive" timeout.
6. Otherwise → `offerRecovery`: the UI *may* offer explicit, user-confirmed, history-only recovery.

**Recovery (user-confirmed, history-only, replaceable).** Candidates cleared to `offerRecovery` are published as `OrphanedWorkout`s; `WorkoutViewModel` mirrors them into the `PendingSyncBannerView` on the History tab. On confirmation, `WorkoutViewModel.recoverOrphanedWorkouts()` re-reads the correlation set (a stale banner can't duplicate a committed workout), then builds a `WorkoutSession` per candidate: routine matched by `RoutineId` (exact) or name, exercises/sets reconstructed from that template (planned values as actuals — HKWorkout lacks per-set detail), the HKWorkout's start/end/external UUID stamped on, noted *Recovered from Apple Health*, saved in the repository. The placeholder gets a **fresh random `id`** (distinct from any watch payload id) and its external UUID as `healthKitWorkoutId`; the coordinator is told via `markPlaceholderSaved(externalUUID:sessionId:)`, which marks the ledger entry `placeholderSaved`. Because the placeholder shares the external UUID but not the id, the existing ticket-04 ingest path recognises a later rich payload as a replacement, deletes the placeholder, and inserts the real per-set data **in one save** — atomic, idempotent, no duplicate row (see "Placeholder replacement" above). The reconciler then advances the ledger entry to `placeholderReplaced` once the committed session id for that external UUID differs from the stored placeholder id.

**Diagnostics + support summary (`WorkoutRecoveryDiagnostics`).** Structured `os.Logger` events keyed by a deterministic, one-way shortened token (an FNV-1a fold of each UUID, stable across launches, never the raw id) — transport path, pipeline phase, HealthKit object token, candidate age, and the concrete error. It logs no exercise names, health metrics, or raw payloads. `WorkoutRecoveryCoordinator.debugSummary()` returns one bounded line per candidate describing its best-known position (`historyCommitted`, `placeholderReplaced`, `placeholder`, `conflict`, `receivedInboxed`, `ingestDeferred`, `outstandingTransport`, `healthKitOnlyCandidate`, `unknown`). Genuinely unknown remote progress stays `unknown` and is **never** inferred from a false `hasContentPending`.

The engine does **not** gate on `HKHealthStore.authorizationStatus(for:)` — that API reports *write* (sharing) status only; HealthKit always returns samples the app wrote itself, so gating on `.sharingAuthorized` would suppress detection/recovery for users who never granted write access.

After a successful ingest save, `.workoutHistoryDidChange` is posted by whichever isolated path committed — `WatchWorkoutIngestionService` for a no-template workout, `WatchTemplateTransactionService` for a template transaction. `WorkoutViewModel` observes this, refreshes its display cache, and re-runs reconciliation. Correlation correctness remains independent of that display refresh: it always comes from the fresh read boundary above.

## Delegate isolation boundary (Swift 6, updated 2026-08-12)

Both `WatchConnectivityManager`s are `@MainActor final class` with every
`WCSessionDelegate` requirement individually `nonisolated`, hopping via
`Task { @MainActor in … }`. That hop mechanism is deliberate and must not be swapped
for `DispatchQueue.main.async` or `MainActor.assumeIsolated`: SE-0431 guarantees tasks
targeting an actor are **enqueued in creation order**, which is what preserves the
callback ordering this protocol depends on, and `assumeIsolated` would trap because
these callbacks genuinely run on WCSession's background queue.

Under Swift 6 strict concurrency **nothing non-`Sendable` may cross that hop**, so each
callback now extracts what it needs *before* the `Task`:

- **`WCSession` flags** (`isPaired`, `isWatchAppInstalled`, `isReachable`) are read
  synchronously in the nonisolated callback; only the resulting `Bool`s are sent. The
  session object itself never crosses.
- **Its *mutable* snapshot state (`receivedApplicationContext`,
  `outstandingFileTransfers`) is deliberately NOT hoisted.** Both are read *inside* the
  hop from the manager's stored `self.session` (the same `WCSession.default` singleton
  the callback receives), so they are sampled at the moment they are used — exactly as
  before the migration. Hoisting them was tried and reverted: it opened a window
  between callback and hop in which a newly started catalogue transfer would be missing
  from `cleanUpOrphanedStagingFiles(keeping:)` and its staging file deleted mid-flight.
  **Do not "optimise" these reads back out of the hop.**
- **`[String: Any]` plist payloads** cross inside `WatchWirePayload`, a documented
  `@unchecked Sendable` transport box in `WatchTemplateTransactionModels.swift` (a copy
  in each target). It deliberately boxes rather than re-typing the dictionary:
  re-encoding plist values into a closed `Sendable` enum would risk silently dropping
  or widening a value this protocol depends on — the routine authority already encodes
  `UInt64` generations as decimal strings because plists are lossy here. Boxing keeps
  the received payload byte-identical and leaves every existing parser
  (`TemplateAckRecord.from(payload:)`, `RoutineSnapshotHeader.parse(context:)`,
  `WatchRoutineSync`, the catalogue challenge readers) unchanged.
- **`ExerciseCatalogInbox`, `WatchWorkoutWire`, `WatchExerciseCatalogSync` and
  `WatchSyncDiagnostics` are `nonisolated`** so the callbacks can reach them. This is
  load-bearing on the watch target, which compiles with
  `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`. `ExerciseCatalogInbox.storeIncomingFile`
  especially **must** stay synchronous in the callback: `WCSessionFile`'s temp file is
  deleted as soon as the delegate returns, and `WCSessionFile` is not `Sendable`, so
  deferring it into the hop would be a bug.

The activation callback's **load-bearing ordering** (challenge update before inbox
drain) is unchanged — extraction happens before the `Task`, the use order inside it is
identical. Full rationale: `docs/swift6-concurrency.md` §4.

## Background lifecycle

`GymStreakWatchApp` registers `.backgroundTask(.watchConnectivity)` → `WatchConnectivityManager.handleWatchConnectivityBackgroundWake()`. Every WatchConnectivity delegate callback synchronously registers its app-owned work with `WatchConnectivityDelegateWorkTracker` before hopping to the main actor, and unregisters it only when that work is complete. The background handler waits for activation, `hasContentPending == false`, and the tracker to become idle, then rechecks both signals before performing the catalogue inbox drain, challenge republication, and workout reconciliation. This is an explicit completion barrier: `hasContentPending` covers undelivered *system* content only, and a single `Task.yield()` cannot prove that already-dispatched delegate work has finished. There is no arbitrary local timeout: the system cancels the task at expiration, at which point every durable input remains replayable for the next wake. SwiftUI completes the background task when the async closure returns — there is no explicit completion call. Watch scene activation also reconciles directly, so reopening a suspended app remains a recovery trigger rather than relying on WCSession's one-time process activation callback.

On the iOS side the ingestion coordinator is created and given a **launch drain** in `AppDependencies.init` — before any `RoutinesViewModel` exists — so a payload left by a prior crash is ingested before the app can push stale routine data to the watch. `WatchConnectivityManager.onWorkoutInboxUpdated` (set by the composition root) re-drains on every receipt and on WCSession activation. Activation and each foreground transition also send the bounded queue-drain request to Watch; this closes the opposite case where no payload reached the iOS inbox while the phone was powered off.

## Exercise Catalogue Sync (iOS → Watch, ticket 03 of in-workout routine editing)

The watch needs the full exercise library (not just the exercises flattened into routines) so ticket 06 can present an exercise picker even while the phone is unreachable. iOS is the source of truth; the watch persists the last valid snapshot.

### Transport: tagged `transferFile`, never `applicationContext`

The catalogue is a versioned JSON document (`WatchExerciseCatalogSnapshot`, schema v1) sent via `WCSession.transferFile(_:metadata:)` with metadata `type == "exerciseCatalog"`. Reasons: `updateApplicationContext` replaces its whole per-direction dictionary (sharing it would couple routine and catalogue sends and bloat every routine payload), and the catalogue (98+ seeded rows plus unbounded custom exercises) has no safe documented size bound for the dictionary transports — Apple documents only `WCError.payloadTooLarge`, no numeric limit. `transferFile` queues without reachability; it needs an activated session and (on iOS) a paired watch with the Watch app installed. Superseded catalogue transfers are cancelled by exact metadata tag — but that is queue pruning only; correctness comes from full replacement + the receiver's recency rules below. **The simulator does not exercise `transferFile`**; transport verification requires paired hardware.

### Recency: authority epochs + generations (not snapshot IDs)

Wire types live in `WatchExerciseCatalogModels.swift` — an **identical file in both targets** (`GymStreak/Data/Sync/` and `GymStreakWatch Watch App/Models/`), including the pure receiver state machine (`WatchExerciseCatalogReceiverState`) so the iOS test target can cover the accept/reject rules (there is no watch unit-test target).

- Each snapshot carries `(authorityEpoch, generation, snapshotID, items)`. Within one epoch, only a strictly higher generation replaces the cache; `snapshotID` is used solely for duplicate suppression and diagnostics (random UUIDs are not orderable).
- The watch publishes a challenge via watch → iOS `applicationContext` (string values: `catalogueWatchInstanceID`, `catalogueCurrentEpoch`, `catalogueCurrentGeneration`, `catalogueHandoverNonce`). It is republished on every activation and rotated only in the same commit that accepts a handover. These keys must be merged into any future watch → iOS context content (whole-dictionary replacement per direction).
- An **unknown epoch** is accepted only through a receiver-authorized one-shot handover: the snapshot must target the watch's `watchInstanceID`, name the watch's exact current epoch as `fromAuthorityEpoch` (nil only for bootstrap), and carry the watch's persisted unused `handoverNonce`. Accepting a handover retires the previous epoch forever (`retiredEpochs`), consumes the nonce, and mints the next one — all in one atomic state-file commit.
- iOS (`ExerciseCatalogSender`) persists `(activeAuthorityEpoch, nextGeneration, proposedAuthority + challenge binding, desiredItems, stagedSnapshot, blockedSnapshotID)` in an atomically replaced Application Support state file **before** enqueueing any transfer; a failed state write enqueues nothing. A mismatching challenge (bootstrap, reinstall, watch switch, restored/retired iOS state) mints a **fresh** proposed epoch bound to that exact challenge tuple — a previously persisted authority is never re-proposed, since the watch may have retired it. When the watch reports the shared epoch at a higher generation than the persisted counter (restored iOS backup), the sender advances to `receiverGeneration + 1`. Generation overflow rolls into a fresh authorized handover. No snapshot is sent until a challenge has arrived; the desired catalogue is retained durably meanwhile.

### iOS triggers and ownership

`ExerciseCatalogSyncCoordinator` (composition root, `AppDependencies.exerciseCatalogSync`) is the single lifecycle owner — deliberately not a view-scoped ViewModel (several `ExercisesViewModel` instances exist, and changes also come from seeding and CloudKit). It fetches fresh committed `ExerciseRepository` state and calls `WatchSyncServicing.syncExerciseCatalog(_:)`. Triggers:

1. `GymStreakApp.onAppear` immediately after `DefaultContentSeeder.run()` (first snapshot can't race seeding/dedup);
2. every successfully committed add/edit/delete/delete-all in `ExercisesViewModel` (its `save()` now returns success; a failed save requests nothing — an uncommitted in-memory snapshot must never reach the watch);
3. the app-lifetime `.cloudKitDataDidChange` observer.

The transport layer (`WatchConnectivityManager` + `ExerciseCatalogSender`) re-enqueues the latest staged snapshot on activation, on challenge arrival/recovery from `receivedApplicationContext`, and on `sessionWatchStateDidChange` reporting a newly available watch. Identical content is suppressed in-process; the persisted staged snapshot is re-enqueued once per iOS launch (the watch treats duplicates idempotently). Reachability is never consulted.

### Failure policy (permanent-for-bytes vs transient)

`WCError.payloadTooLarge` / `.payloadUnsupportedTypes` / `.invalidParameter` and local encode/write failures are **terminal for those exact bytes**: the snapshot ID is persisted as blocked, lifecycle triggers will not hot-loop it, and only changed catalogue content (or a code fix) unblocks. All other errors are transient: the staged snapshot stays replayable, retried with bounded backoff (3 attempts) and on lifecycle triggers. A snapshot superseded by a newer one never requeues itself. Sender staging files (`Application Support/ExerciseCatalogSync/Staging/`) live until that transfer's `didFinish` callback; orphans are cleaned at activation, keeping URLs still referenced by `outstandingFileTransfers`. This classification is deliberate app policy — Apple documents no permanent/transient taxonomy. Chunking is deliberately NOT implemented; add it only if paired-hardware testing demonstrates a real size ceiling.

### Watch receive path (crash-resilient inbox)

`session(_:didReceive:)` (watch `WatchConnectivityManager`) checks the metadata tag and **synchronously moves** the system-owned temporary file into an owned App Group inbox (`ExerciseCatalog/Inbox/`, arrival-ordered filenames) before the callback returns — an in-memory copy could still be lost to suspension before persistence. `ExerciseCatalogStore` (sibling of `RoutineStore`, but file-based) drains the inbox serially on the main actor: full decode + schema/target/handover/epoch/generation validation via the shared state machine, then an atomic replacement of the single state file (`ExerciseCatalog/state.json`), then publication to observers, and only then deletion of the inbox file. Malformed/unauthorized/stale deliveries are quarantine-deleted with diagnostics and never touch the last-good cache; transient persistence failures leave the inbox file replayable. A valid **empty** snapshot clears `items` but keeps `hasReceivedCatalog == true` — never-synced (`items == nil` in state) and valid-empty are distinct, and the distinction survives relaunch.

The store is owned by the watch `WatchConnectivityManager` (lazy) — not by `AppState` — so a cold background wake without UI still has exactly one store/inbox owner; `AppState.init` references it so it exists (and drains) before any view appears, and injects it into the environment for ticket 06. Store exposes: `items`, `hasReceivedCatalog`, `lastSyncDate`, `lastSnapshotID`, `lastAuthorityEpoch`, `lastGeneration`.

`GymStreakWatchApp` registers `.backgroundTask(.watchConnectivity)`: the handler waits for activation and `hasContentPending == false` (system queue only — not our app-level work), then runs the synchronous inbox drain + challenge republication before completing. On cancellation it stops cleanly; owned inbox files survive to the next launch. This closes the old cold-launch gap where stores were only attached from the root view's `.task`.

## Template Transactions (ticket 05)

"Save & Update Template" is an ordered, all-or-nothing **template transaction**, not a best-effort side effect of ingesting history. The durable unit is `TemplateTransactionEnvelope` (`transactionID`, sender epoch, routine, sequence, optional workout correlation, extensible payload), not `CompletedWatchWorkout`; ticket 05 implements only `.completedWorkoutUpdate`. Ticket 07 extends that payload with structural intent, and a later template-only kind reuses the same FIFO, inbox, receipt ledger, acknowledgment protocol, executor phases, and routine authority instead of adding a second protocol.

### Ordering identity (watch)

When the frozen payload is enqueued, the **same atomic commit** allocates the transaction's identity and retains the routine anchor:

- `templateTransactionID` — stable across retries, the semantic transaction identity. The workout id is only correlation (a template-only kind has none).
- `templateSenderEpoch` — one persistent per-install epoch shared by every template-mutating kind.
- `templateSequence` — monotonic **per routine** within that epoch.

All three also remain optional on the embedded legacy workout wire copy, so old payloads stay decodable and an old iOS build ignores them. New builds prefer the generic envelope while sending the workout copy alongside it for mixed-version compatibility. Entries queued before ticket 05 are converted to transaction envelopes in their existing FIFO order in the same atomic replacement that commits the counters; a failed replacement publishes no challenge and transports nothing.

Only the **oldest pending transaction per routine** may be transported (over either path); the next is released when the head retires. A migrated queue can already have multiple transfers in flight, so acknowledgments are also retired strictly as a satisfied per-routine FIFO prefix—an overtaking successor remains held behind its head. No-template workouts are independent because they cannot mutate a routine. The sender gate is *not* the ordering authority: Apple documents queued transfers as ordered and messages as higher priority, but not causal ordering across the two, so a delayed background duplicate can still overtake. Receiver sequence enforcement plus durable receipts are what make a late duplicate acknowledgment-only.

### One-save commit (iOS)

`WatchTemplateTransactionCoordinator` gates on the per-`(senderEpoch, routine)` sequence ledger: a **higher** sequence stays durably inboxed without mutating anything; a **lower** one must resolve from its receipt (a missing lower receipt is surfaced, never guessed); a ledger that does not exist yet is bootstrapped by the first observed sequence — which is what keeps an iOS reinstall from deadlocking against a watch that kept its counters.

`WatchTemplateTransactionService` (Domain) then validates the **complete** set-only intent against the current routine *before* mutating: a missing routine, routine exercise, alternative, or set rejects the whole request rather than applying part of it. History and the template update stage in one isolated `autosaveEnabled = false` context and `save()` **exactly once**. A rejection still saves history, leaves the routine byte-for-byte untouched, and records `didUpdateTemplate == false`.

That same save writes optional `WorkoutSession.watchTemplateTransactionID` and `watchTemplateOutcomeRaw` witnesses. On a post-save/primary-receipt failure, replay trusts those fields only when the transaction ID matches, so it can reconstruct the receipt without reapplying old values over a newer user edit. A legacy row has nil witnesses even if its older build set `didUpdateTemplate = true`; it therefore runs upgrade reconciliation instead of falsely claiming the former separate template save succeeded. These are additive SwiftData/CloudKit attributes with nil defaults. Release requires Development schema initialization and manual Development → Production deployment in CloudKit Console (`docs/cloudkit-schema-automation.md`).

Only a save failure rolls back. Everything after the commit is phase-resumable:

| Receipt phase | Meaning |
|---|---|
| `committedAwaitingContext` | Local outcome is final and durable; resumes only authoritative context staging, never re-mutation |
| `readyToAcknowledge` | The authoritative routine snapshot was staged; carries the exact epoch/generation. Acknowledgment-only from here on |

Receipts are keyed by `(senderEpoch, routineID, sequence)` with an optional workout id kept only as a secondary correlation index, and are retained indefinitely for the same reason as ticket 04's. Before resume, the stored transaction ID—and workout correlation when both sides carry one—must match the incoming envelope; a same-sequence/different-ID collision remains inboxed as a consistency error. Receipt, correlation-index, and sequence-ledger operations are O(1) rather than rewrites of one growing blob. Because those files cannot be replaced as one filesystem transaction, every receipt resume first idempotently repairs its index and expected-sequence ledger; no ack/removal occurs until that repair succeeds. A `ReadyRecovery/` marker set is proportional only to terminal transactions whose correlated watch generation has not yet been proven; it prevents authority changes from scanning the indefinite receipt history.

### Versioned acknowledgment

Only after the post-commit routine snapshot is staged does iOS send the terminal acknowledgment (property-list-safe strings): optional `workoutAck`, `templateUpdateVersion`, `templateTransactionID`, `templateOutcome` (`applied` | `rejected`), `templateSenderEpoch`, `templateSequence`, `routineSyncEpoch`, `routineSyncGeneration`. `applied` means the request committed (or was already reconciled idempotently); `rejected` means a deliberate terminal decision left the routine untouched. A transient failure sends **no** terminal acknowledgment at all.

Because the workout id still travels under the legacy `workoutAck` key, an old watch reads it as a plain acknowledgment. Conversely a **plain** acknowledgment never clears template intent on a new watch: an old iOS build acknowledged history without processing the template, so those entries stay queued and are re-sent on lifecycle triggers until iOS is upgraded.

### Routine authority + optimistic fold (both targets)

Routine `applicationContext` snapshots are versioned exactly like the catalogue's: `(routineSyncEpoch, routineSyncGeneration)`, with an unknown epoch acceptable only through a receiver-authorized one-shot handover bound to the watch's exact challenge tuple (target instance, from-epoch, unused nonce). Both version keys absent means a legacy context; any partially present or malformed required/optional authority field rejects the context rather than downgrading it to trusted legacy. `RoutineSyncAuthority` (iOS) is the single serialized generation owner and durably consumes a generation/proposal **before** handing it to WatchConnectivity; persistence failure sends nothing, an ambiguous transport failure never reuses a generation, and `UInt64.max` performs a fresh handover. Ordinary list syncs and authoritative post-commit snapshots both go through it. Old watches that publish no challenge still receive a legacy unversioned ordinary snapshot.

If a later challenge proves that a receipt's proposed epoch/generation was not accepted, the composition-root authority-change hook scans only unresolved ready-recovery markers, restages **current authoritative routines** under the new challenge, replaces each receipt's correlated version, and resends its acknowledgment without repeating history/template mutation. A matching challenge removes the marker but retains the dedupe receipt. Ordinary inbox drains do not scan ready history, preventing acknowledgment amplification.

On the watch, `WatchSyncStateStore.effectiveRoutines()` = newest accepted base with every unresolved transaction folded back over it. That is why an ordinary or legacy context can never erase a pending optimistic value, and why `RoutineStore` no longer persists its own copy — it is a published projection of that computation. A terminal acknowledgment is **held** until the watch has applied the routine generation it names, so ack-first and context-first delivery converge identically; only then does the head retire and release the next transaction.

The Watch UI treats routine identity and routine values differently. `RoutineListView` stores only a typed routine ID in `NavigationStack` and resolves the current value from `RoutineStore` while a detail is visible. Starting a workout resolves that ID once more inside `WatchWorkoutViewModel`; only then is the routine copied into active-workout state. This is the intentional snapshot boundary: later routine contexts update future workouts, never a session already in progress. Storing a full `WatchRoutine` in the path is forbidden because SwiftUI path values are snapshots and have no live relationship to a later published replacement. This follows Apple's [navigation-stack guidance](https://developer.apple.com/documentation/swiftui/understanding-the-navigation-stack) to use lightweight identifiers. `updateApplicationContext(_:)` remains the correct authoritative transport: Apple documents it as opportunistic, coalescing latest-state delivery, not an event stream or an immediate-delivery API ([API reference](https://developer.apple.com/documentation/watchconnectivity/wcsession/updateapplicationcontext(_:))). Relaunch-time `receivedApplicationContext` replay is recovery, not a requirement for live delivery.

### Mixed-version payloads

A requested-template payload without ordering identity (old watch build) may run the idempotent set-only reconciliation only while **no** sequenced outcome exists for its routine. Once one does, it can no longer prove it is newer: history is preserved and deduplicated, `didUpdateTemplate` is corrected to false, current routine state is staged, and the intent is answered with the plain acknowledgment its sender understands. Successful no-receipt legacy reconciliation similarly corrects the flag to true.

**Swapped alternatives (bug fixed 2026-07-11):** when the performed exercise was an alternative (`plannedExerciseId != nil` on the completed exercise), its set ids belong to the alternative's own scheme (`WatchExerciseAlternative.sets` / `AlternativeExerciseSet`), NOT the primary's sets. Both template-apply sites therefore branch on the swap: `WatchTemplateTransactionService` resolves the matching `RoutineExerciseAlternative` (via `exercise?.id == completedExercise.exerciseId`, sets matched by id — `AlternativeExerciseSet.id` survives the whole round-trip), and the watch-side `WatchRoutineTemplateFold` writes them into the matching entry of `WatchExercise.alternatives`. Before the fix, the id lookup against the primary's sets silently failed ("Could not find set with ID") and choosing "update routine" after a swapped watch workout changed nothing.

**Legacy placeholder repair.** An older build inserted a placeholder `Routine` when the target routine had been deleted. Such a row is deleted only under the strict contradiction signature — created *after* the workout ended, named exactly like the workout's routine, no exercises, and no schedule — and the transaction then behaves as "routine missing". Name or emptiness alone is deliberately insufficient: a real, still-empty routine the user just created must never be deleted.

### Structural add/remove intent (ticket 07)

Ticket 07 extends the completed-workout transaction with explicit structural membership intent, reusing the envelope, FIFO, receipts, executor, acknowledgment, and routine authority above unchanged.

*Wire.* `CompletedWatchWorkout` gains optional `addedRoutineExerciseIDs` / `removedRoutineExerciseIDs`, and `CompletedWatchExercise` gains optional `exerciseSeedKey` (both `WatchModels.swift` copies stay wire-identical). Additions are emitted in final exercise order (minted slot UUIDs, each present in `exercises`); removals are emitted in workout-start baseline order (each absent from `exercises`). Optional decoding keeps old-watch/new-iOS payloads readable as set-only, and the Data→Domain mapper normalizes absent arrays to empty. Deletion is *never* inferred from a stale omission — only an explicit removal ID deletes.

*Watch optimistic fold.* `WatchRoutineTemplateFold.apply` now also deletes explicitly-removed slots (with the same superset cleanup — ≥2 remaining renumber and keep the group UUID, a lone survivor is cleared), appends an addition only when its minted slot UUID is absent (idempotent under retransmission/duplicate delivery), marks each added slot `isPendingWatchAddition == true`, preserves unrelated slots added concurrently on iOS, and normalizes order. A pure set-only fold is byte-for-byte unchanged. Pending provenance survives relaunches and later workouts (ticket 06's baseline keeps pending slots in the *known* baseline so they retransmit and a later removal can cancel them) and clears only when the correlated ack **and** authoritative generation retire the transaction.

*Verification status (ticket 07).* Automated: `GymStreakTests/WatchStructuralTemplateTests.swift` (wire backward-compat + membership/seed-key mapping, the watch fold's structural behavior incl. superset cleanup/idempotency/pending overlay, and the iOS merge's resolution/rejection/concurrent-preservation/idempotency) — full suite green, both schemes compile, architecture review PASS WITH WARNINGS (file-length only, resolved by the fold/validation extractions). Paired-hardware matrix **passed 2026-07-23** on a physical iPhone + Apple Watch pair: reachable add/remove persistence (both platforms converge; decline-template stays session/history-only); powered-off / unreachable / suspended / force-quit iPhone and watch-relaunch-before-ack recovery; a pending addition reused in a second offline workout and later explicitly cancelled; concurrent iOS edits preserved and an iOS-deleted slot never resurrected; remove-then-re-add; two- and three-member superset dissolution/renumber; a library exercise deleted mid-workout rejecting the whole template while saving history and clearing the optimistic row; and rejection / latest-wins convergence — with correct pending-sync counts and no duplicate history.

The isolated transaction now also exposes an `ExerciseRepository` over its own context (`WorkoutHistoryTransaction.exerciseRepository`) so a resolved exercise and the new slot commit in one save. `applyStructural` then merges only explicit intent against the **current** routine: removed slots + child sets are deleted through repository APIs with the current superset dissolved/renumbered immediately, additions are inserted with the Watch-minted slot/set UUIDs (insert-before-wiring), linked to the canonical library exercise, with copied actual values and standalone (no alternatives/rep-range/superset), and every other current slot — including concurrent iOS additions/reorders — is preserved. A retained Watch slot iOS deleted concurrently is a no-op (never a re-add). Any malformed/dangling/overlapping intent or unresolvable library identity rejects the whole request (history saved, routine byte-for-byte untouched, `didUpdateTemplate == false`); the authoritative context then removes the optimistic Watch row. The merge is idempotent: a re-drain short-circuits on the atomic transaction witness, and the minted-slot-absent guard + already-absent removals + value-set updates make a legacy re-apply safe.

### Rest duration intent (watch-rest-adjust ticket 04)

A rest duration adjusted on the watch mid-workout (Digital Crown or the minimized pill's stepper — see `docs/watch-rest-timer-ui.md`) reaches the routine through this same completed-workout transaction, gated by the same **Save & Update Template** choice. No new transaction kind, queue, receipt, acknowledgment or ordering rule: rest is one more field the existing envelope carries.

*Wire.* `CompletedWatchSet` gains optional `plannedRestTime` — the rest the set started the workout with — alongside the existing `restTime`, which now carries what was actually rested for (both `WatchModels.swift` copies stay wire-identical, and `IncomingWatchSet` mirrors it). The **pair** is the point: `restTime != plannedRestTime` is *explicit intent*, exactly as `plannedReps`/`actualReps` is for values. Diffing the payload against the live template instead would read a concurrent iPhone rest edit as watch intent and silently revert it, which the transaction's "only explicit intent is merged against the current routine" contract forbids. Optional decoding keeps old-watch payloads readable: absent baseline ⇒ no rest intent, never a write.

*One value per exercise, never per set.* The app models a single rest duration per exercise everywhere (routine editor, watch write path, iOS `RoutineTemplateSyncService.updatePrimaryTemplateSets`), so both the fold and the merge take the performed exercise's **first set's** `restTime` and write it to that exercise's whole scheme — template sets that were never performed included. A superset round's rest is written by the watch to every member of the group (ticket 01's fan-out), so the payload already carries the new value on each slot and the merge needs no superset rule of its own.

*Change detection (watch).* `ActiveWorkoutSet.wasRestModified` is deliberately **not** folded into `wasModified`: a rest change is one change per exercise, so counting it per set would inflate the finish dialog's "you modified N sets". It surfaces instead as `WatchWorkoutViewModel.hasRestChanges` → `hasTemplateChanges`, and as the new `WatchWorkoutFinishDialogState.restOnly` ("You changed the rest time. Update your routine template?"). Rest is the weakest of the three signals — any set or structural change already offers the update and the rest rides along with it — so `.restOnly` is reached only when nothing else changed.

*Overload exclusion — rest rides alongside it, it is not subject to it.* An exercise in `overloadAppliedExerciseIDs` stays excluded from generic set-value writeback, but its rest **is** written, in both the watch fold and the iOS merge. The progressive-overload transaction commits reps and weight only; there is no rest value of its own for a replay to regress. This is also what iOS already does for an iPhone workout — `updatePrimaryTemplateSets` assigns `restTime` outside its `writesSetValues` guard.

*iOS merge.* `WatchTemplateTransactionService.SetUpdate` now carries optional `reps`/`weight` plus an optional `restTime`, and `apply` writes only the non-nil fields — the two kinds of intent do not cover the same rows (performed values reach performed sets; a rest change reaches every set of the exercise, including an overload-resolved one). `validateMerge` resolves rest into the same all-or-nothing plan: it emits an update only for sets whose rest actually differs (so a redelivery is a no-op and untouched rows are never dirtied), targets the swapped exercise's **alternative** scheme when the slot was swapped, and leaves the pre-existing rejection rules untouched — a malformed request still rejects wholly with history saved and the routine byte-for-byte untouched. No `@Model` schema change: `ExerciseSet.restTime` / `AlternativeExerciseSet.restTime` already existed, so no CloudKit schema deploy is involved.

*The main-context mirror is load-bearing, not a cache (root cause, 2026-08-11).* A paired-simulator pass found rest changes silently not persisting while reps/weight always did — and the cause is not in this feature at all. A transaction commits in an **isolated sibling context**; once the app has been running long enough for the MAIN context to have saved those same `ExerciseSet` rows, the sibling's attribute writes lose the row-version conflict at save and are **discarded silently**. Everything else in the same save still lands (the `WorkoutSession`, its `WorkoutSet` rows, `Routine.updatedAt`), so the transaction reports `applied`, the receipt is written, the watch is acknowledged — and the routine is unchanged. What actually establishes the committed values in the store is `SwiftDataMainContextRoutineCacheRefresher.refreshCache`, which mirrors the authoritative snapshot into the main context and saves it. It had only ever copied `reps` and `weight`, so those survived and rest reverted to whatever the main context last held (which is also why the reverted value looked like an unrelated default). **Any field added to `WatchSet` must be mirrored there too.** Guarded by `GymStreakTests/WatchRoutineCacheRefreshTests.swift`, which is deliberately file-backed: an in-memory store performs no such conflict resolution, so this class of bug passes every in-memory test and only appears on device.

*Diagnosing a template transaction from the field.* Three unified-log lines, readable with Console.app or `xcrun simctl spawn <device> log show --predicate 'subsystem == "com.shotat24fps.GymStreak"'`, and no debugger: the watch's `finalize: template intent — N modified set(s), rest changed on M exercise(s) [slot=performed/baseline …]` says what was sent; the iPhone's `ingest: split template <outcome> — rest intent on M exercise(s) […]` says what arrived; and `merge: slot <token> rest intent <value> slotFound=… alreadyAtValue=… swapped=…` plus `merge: committed N update(s), K with rest` say what the merge resolved and whether it wrote anything. All three carry the SAME one-way slot token, so they join on slot identity. Reading them together separates the three ways this can fail: no watch line ⇒ the watch never recorded it; a watch line but no ingest line ⇒ it never arrived (check the watch's FIFO head — a finalized entry is withheld behind an unretired transaction); an ingest line with `slotFound=false` or `alreadyAtValue=true` ⇒ the merge had nothing to write; and `K > 0` with the store unchanged ⇒ the commit was lost, which is the conflict above. The merge lines reach the log through `WatchTemplateTransactionService.diagnostics`, injected at construction as `WatchTemplateTransactionCoordinator.mergeDiagnosticSink`. It takes the slot as a `UUID?` rather than a formatted string: Domain must not import the Data-layer logger, and shortening identifiers into one-way tokens is that logger's privacy boundary — a raw UUID logged from Domain would breach it AND print under a different token than the other two lines, which is the one thing the trail exists to prevent. (A `print` would also be invisible on device.)

Full suite green (457 tests); both schemes compile. **Paired-hardware pass 2026-08-11** (physical iPhone + Apple Watch, after the same pass on a simulator pair)**:** rest changed on the watch, finished with Save & Update Template, and the iPhone routine plus the watch's next baseline both converge on the new value — confirmed after the mirror fix above, with the watch/iPhone/merge log lines agreeing at every hop.

### Progressive-overload intent — a template-ONLY kind (progressive-overload ticket 04)

Ticket 04 adds the first transaction kind that carries **no completed workout**, proving the generic seam ticket 05 reserved. It adds no queue, inbox, receipt ledger, acknowledgment protocol, routine authority, or lifecycle owner: the envelope, per-routine sequence, FIFO head gate, transport paths, serialized inbox, receipt phases, versioned ack, and routine authority above are all reused unchanged. Product behavior and the design flow live in `docs/rep-range-progressive-overload.md`; this section is the protocol delta.

*Wire.* `TemplateTransactionPayload` gains `.progressiveOverload(WatchProgressiveOverloadIntent)` (`WatchProgressiveOverloadModels.swift`, identical copy in both targets). The intent carries `schemaVersion`, `routineExerciseID`, an optional `alternativeID`, `targetRepMin`, and `setChanges` of **absolute** `expectedReps/Weight` + `proposedReps/Weight` — never deltas, so duplicate delivery cannot increment twice. Expected values are derived from the latest *effective* routine template scheme (authoritative base + pending optimistic overlay), never from the workout's performed values.

*The envelope's `workoutID` MUST be nil for this kind.* `TemplateTransactionEnvelope.isInternallyConsistent` already required it for any payload without a workout, and `WatchWorkoutInboxStore.store(transactionData:)` rejects a violation. This is not cosmetic: `WatchSyncStateStore.entry(id:)`, `advance`, `quarantine`, and `retire` all match on `workoutID`, so an overload envelope carrying the active workout's id would make the later `enqueue(workout)` return the overload entry instead — silently dropping the completed workout entirely (no history, no HealthKit ingest). Source-workout correlation, if ever needed, belongs inside the payload.

*Watch enqueue.* `WatchSyncStateStore.enqueue(progressiveOverload:routineID:transactionID:routineAnchor:)` commits the exact payload bytes, the next per-routine sequence, the FIFO position, and the held routine anchor in one atomic replacement, then returns a `.transportEligible` entry (there is no HealthKit finalization to phase through). `transactionID` is caller-supplied and is the dedup key, so repeated taps and post-crash recovery reuse one transaction instead of allocating a second sequence. A failed write throws with nothing enqueued and the counter rolled back. `effectiveRoutines()` folds the new kind through `WatchRoutineTemplateFold.apply(intent:to:)` alongside completed-workout intent, in FIFO order, so the optimistic overlay matches the order iOS will apply them in; the fold is idempotent and leaves a set the base has moved to a third value alone.

*iOS receive.* `WatchWorkoutIngestionCoordinator.process` already routed payload-less entries to the template coordinator; `WatchTemplateTransactionCoordinator+ProgressiveOverload.swift` replaces the former "unsupported payload retained" bail. It runs the same ordering-ledger gate, isolated single-save transaction, `committedAwaitingContext` → `readyToAcknowledge` receipt phases, and versioned terminal ack. The only structural difference is that the receipt has nil `workoutId`/`healthKitWorkoutId`; `WorkoutIngestReceiptStore` keys such a receipt by its transaction identity and skips the correlation indexes.

*Wire → Domain boundary.* As with the completed-workout kind, the Domain layer never sees the Codable sync type: `WatchProgressiveOverloadIntent.toIncomingProgressiveOverload()` (iOS copy of `WatchProgressiveOverloadModels.swift` only — the watch has no Domain layer) maps it into `Domain/Models/IncomingProgressiveOverload.swift` at the coordinator, exactly as `CompletedWatchWorkout.toIncomingWatchWorkout()` does. The mapping is deliberately **total**: an unsupported `schemaVersion` is carried as `isSchemaSupported == false` rather than mapped to nil, so the receiver can still identify the transaction and answer it with a versioned terminal rejection instead of leaving the watch's entry pending forever.

*iOS apply.* `WatchTemplateTransactionService+ProgressiveOverload.swift` resolves the target by stable id only (slot, then the alternative's own scheme when `alternativeID` is set — never by display name) and compares each set against the **current** template: equal to `expected` → stage `proposed`; equal to `proposed` → idempotently satisfied; a third value, or a missing routine/slot/alternative/set → **reject the whole transaction** with the routine byte-for-byte untouched. It never fabricates history for a transaction that has no workout. Float comparison uses `IncomingTemplateSetChange.weightsMatch` (1e-4), far below any real weight step; the watch fold uses the wire-side twin `WatchTemplateSetChange.weightsMatch`, and a parity test keeps the two validation/tolerance rules from drifting.

*Ordering against completed workouts.* Both kinds share one per-routine sequence, so a mid-workout overload at N is applied before a later "Save & Update Template" workout at N+1 and cannot be overtaken by cross-channel delivery. Accepted consequence: while an overload is pending (iPhone off), that routine's later *template* workout waits behind it — identical to two consecutive template workouts today. A workout saved without the template update carries no template intent, is never FIFO-gated, and reaches History immediately.

*Non-regression.* `CompletedWatchWorkout` gains optional `overloadAppliedExerciseIDs`. Those slots are excluded from generic set-value writeback in **both** `WatchTemplateTransactionService+Validation.validateMerge` and the watch fold, so the completed workout's performed values can never replay over the template weights the overload transaction committed. On ingest the same list sets `WorkoutExercise.progressiveOverloadApplied`, which is what makes history/volume/charts/records/AI read the performed values back out of the planned fields. Rationale in `docs/rep-range-progressive-overload.md`.

*Mixed versions.* New Watch + old iOS: the added payload case fails to decode, `store(transactionData:)` throws, nothing is acknowledged, and the Watch retains the transaction in its atomic FIFO until iOS is upgraded (same policy `acknowledgePlain` applies to template intent) — note it stays FIFO head, so that routine's later template transactions wait behind it. Old Watch + new iOS: absent fields decode as no overload intent.

### Applying an overload from the post-workout recap (progressive-overload ticket 05)

The Watch recap can apply the same increase after the completed payload is already frozen. It reuses this protocol **entirely unchanged** — same envelope, transaction identity, per-routine sequence and FIFO, receipts, acknowledgment and routine authority — and adds only an optional correlation hint.

*Wire delta.* `WatchProgressiveOverloadIntent` gains additive optional `sourceWorkoutID` + `sourceRoutineExerciseID` (nil for a mid-workout apply). No schema bump: an older receiver decodes and ignores them. `isWellFormed` rejects a half-filled pair. They live in the **payload, not the envelope** — `TemplateTransactionEnvelope.isInternallyConsistent` requires `workoutID == nil` without a workout, and a non-nil value there would collide with the workout-id matching `entry(id:)`, `advance`, `quarantine` and `retire` use.

*What it is for.* A recap increase never amends the frozen `CompletedWatchWorkout`, so the recorded workout carries no trace of it and iOS History would offer the same increase again. On `.applied`, `WatchTemplateTransactionCoordinator+ProgressiveOverload` writes `workoutID → [slotID: AppliedOverloadRecord]` into `WorkoutIngestReceiptStore`'s `OverloadCorrelation/` directory (`WorkoutIngestReceiptStore+OverloadCorrelation.swift`, same indefinite retention as the receipts beside it); `WorkoutDetailView` reads it via the `AppliedOverloadCorrelationReading` Domain protocol — `async`, off the main actor — and renders the card's confirmed state. `newWeight` is optional and stays optional: a nonuniform (pyramid/drop) scheme is recorded as applied *without* a weight, and the card shows `rep_range.overload_card.all_sets_adjusted` rather than naming a number that is wrong for every set but the first. It is a **display hint only** — non-throwing, and no failure here may undo an applied transaction. It never creates, requires or alters history, and it deliberately does **not** set `WorkoutExercise.progressiveOverloadApplied` (that flag would redirect every aggregator to `planned*`, which for a recap apply still holds the original template values — see `docs/rep-range-progressive-overload.md`).

*Ordering.* Written on apply, read on display, so it is order-independent — which is required, because a recap overload is `.transportEligible` immediately while a history-only workout is still awaiting HealthKit and is not FIFO-gated. The overload genuinely can reach iOS before its own workout, or before that workout is ingested at all.

*Watch-side pending lookup.* `WatchSyncStateStore.hasPendingTransaction(id:)` exposes only presence, so the recap can tell "still converging" from "iOS has ruled". Once the entry is retired, the effective routine itself is the verdict — no outcome ledger exists or is needed.

### Split template intent — history and template as two entries (history/template split, tickets 01 + 02)

The decision, its alternatives and its consequences are in `docs/adr/0001-split-workout-history-from-template-intent.md`; read it first. Summary: a template-carrying workout produces **two** sync entries — the workout history as an ordinary ungated workout payload, and the template intent as a gated template-only transaction — so a template acknowledgment that cannot be sent costs a template update and never a workout. Ticket 01 shipped the **iOS acceptance half** first, deliberately: iOS acceptance can then reach users in an earlier build than watch emission, so the version-skew stall below never happens in the field. Ticket 02 flipped the watch over to emitting both.

*Wire.* `TemplateTransactionPayload` gains `.workoutTemplateIntent(WatchWorkoutTemplateIntent)` — the whole `CompletedWatchWorkout` plus a `sourceWorkoutID` correlation (always `workout.id`). Wrapping the entire workout is deliberate: it leaves `validateMerge`/`apply`/`applyStructural` and the history dedupe completely untouched, and duplicating a few KB on the wire buys that. `TemplateTransactionEnvelope(templateIntentFor:)` builds it with the ordering identity the fused kind would have used and `workoutID` **nil**.

*The two identity rules, both load-bearing.*

1. **The envelope's `workoutID` is nil, and `completedWorkout` stays nil for this kind.** `WatchSyncStateStore.entry(id:)` matches on `workoutID` as well as the entry id, so a correlated envelope would make the second `enqueue` for a workout return the first entry — silently collapsing the split back into one. `OutgoingSyncEntry.workoutID` derives from `completedWorkout`, so the rule is enforced at the accessor: **`completedWorkout` means "this entry carries history"**. The wrapped workout is reached through `templateIntentWorkout` instead, by exactly two consumers — the iOS routine merge and the watch's optimistic fold. `isInternallyConsistent` accepts the new kind when `workoutID == nil`, `sourceWorkoutID == workout.id`, and the envelope's ordering identity matches the workout's template fields; the fused rule (`workoutID == workout.id`) is unchanged, so a legacy payload whose correlation disagrees with its own workout is still rejected.
2. **The receipt carries no workout correlation** (`workoutId`/`healthKitWorkoutId` nil, as for progressive overload), so `WorkoutIngestReceiptStore` keys it by transaction identity and writes no workout/HealthKit index. A workout-correlated template receipt would answer the *separate history entry* from the wrong receipt and reply with a versioned template acknowledgment — which carries `workoutAck` only when it has a workout id — leaving the history entry unretired on the watch forever. Accepted consequence of the nil `healthKitWorkoutId`: in the template-before-history window the committed session has no HealthKit-correlated receipt, so if the history half never arrives *and* the user deletes that session, HealthKit recovery can offer the workout again. While the session exists, recovery resolves it from history as before.

Second accepted consequence, on the same accessor: `WatchWorkoutInboxStore.Entry.completedWorkout` is nil for this kind too, so a template-only entry sitting in the iOS inbox does not appear in `WatchConnectivityManager.pendingWorkouts()` and therefore does not count as `bufferedIDs` evidence for `WorkoutRecoveryCoordinator`. In the narrow window where the template half is inboxed (or buffered behind a predecessor sequence) and the history half has not arrived, the orphaned-workout banner can offer a workout whose data is already on the phone. It self-heals — `stageHistory` replaces the reconstructed placeholder when either payload commits — and it is strictly better than the fused behaviour it replaces, where nothing arrived at all.

*iOS receive.* `WatchTemplateTransactionCoordinator.process` routes the kind to `WatchTemplateTransactionCoordinator+WorkoutTemplateIntent.swift`, which runs the same ordering-ledger gate, isolated single-save transaction, `committedAwaitingContext` → `readyToAcknowledge` phases and versioned terminal ack as every other kind. It reuses the **completed-workout executor** (`WatchTemplateTransactionService.execute`) unchanged, and that is what makes the two payloads converge in either arrival order: `stageHistory` commits the wrapped copy when the history entry has not arrived yet, and dedupes against the committed session when it already has (falling through to the idempotent reconciliation branch, since a history-only ingest writes no atomic transaction witness). The history entry then still receives its own plain acknowledgment.

*The watch emit path (ticket 02).* `WatchSyncStateStore.enqueue(_:phase:routineAnchor:)` is the split point. For a workout with `shouldUpdateTemplate == true` it appends **both** entries and persists once, so the payload bytes, the transaction identity, the per-routine sequence, the FIFO position and the routine anchor still commit or fail as one unit — a failed write enqueues neither half and consumes no sequence number. A workout without template intent is untouched: one entry, exactly as before. Details that are load-bearing:

- **The history half** is `workout.withoutTemplateIntent()` — same workout id, exercises, end time, HealthKit external UUID, structural and applied-overload slot IDs, but `shouldUpdateTemplate == false` and **no** transaction identity. If it kept the intent, iOS would route it back into the template path and consume the same sequence twice. (With `shouldUpdateTemplate == false` the retained structural/overload IDs are historical metadata and mutate no routine — iOS needs them to record the workout correctly.)
- **`enqueue` returns the history entry**, because that is the half the finalizer sequences HealthKit on: `advance(id:)`, `quarantine(id:)` and `entry(id:)` all match the workout id, which only the history half owns. The idempotent early return (`entry(id: workout.id)`) therefore still collapses a retry onto the frozen pair without creating a third entry.
- **The template half is `transportEligible` immediately.** Its bytes are complete and it has no HealthKit step to wait for (same as progressive overload), and it is unreachable from `advance(id: workoutId)` anyway. A consequence worth knowing: it can reach the iPhone while the workout's own history entry is still in a HealthKit phase — iOS then commits the history from the wrapped copy, which is exactly the template-before-history order ticket 01 made converge.
- **Nothing else changed.** Transport, retirement, quarantine, the plain/versioned acknowledgment split and the optimistic fold all worked unmodified, which was the design's own falsifiable prediction (if a transport or retirement rule had needed editing, the entries would have been shaped wrong). One visible behavior shift follows from it: `acknowledgePlain` now *does* retire the history half of a template-carrying workout — that half is an ordinary workout payload. Its template-intent guard still protects **legacy fused** entries, whose single payload carries intent an old iOS build never processed.

*Watch optimistic fold.* `effectiveRoutines()` folds the new kind through `WatchRoutineTemplateFold.apply(workout:to:)` via `templateIntentWorkout`, in the same FIFO order, so an accepted change stays visible while in flight. The history entry carries no template intent and therefore never folds — no double overlay.

*Nothing is migrated.* The split happens at enqueue time; entries frozen by an earlier build stay fused and drain through the `.completedWorkoutUpdate` handling, which remains for older watches regardless.

*Mixed versions.* New Watch + old iOS: the added payload case fails to decode, `store(transactionData:)` throws, nothing is acknowledged, and the watch retries indefinitely — that routine's template queue head stays pinned until iOS updates, at which point it drains on its own. History is unaffected in every skew combination, since it travels as a payload old builds already understand. Old Watch + new iOS: the fused kind is unchanged.

That second case is the incident this split exists to eliminate, confirmed on real hardware.

#### Telling the user a template update was not applied (ticket 03)

The split makes one failure quieter, by design: a template update that can never be applied no longer withholds the workout, so nothing loud happens — the workout arrives, the watch's optimistic value silently reverts, and a weight increase the user accepted is discovered missing a week later. **Terminal template outcomes are therefore surfaced; pending stays completely silent**, because pending is the normal state for every workout performed away from the phone and a syncing indicator would be in the user's face constantly (that was decided and rejected in ADR 0001).

*What produces a notice.* Exactly the two terminal states, both recorded in `WatchSyncStateStore` in the **same atomic write** that makes them terminal, so a notice can neither outlive its cause nor be lost with it:

1. A held acknowledgment whose outcome is `rejected`, at the moment its correlated routine generation applies and the entry retires (`retire(ids:rejected:)`). `applied` says nothing — the change is simply there.
2. A quarantined entry that carries template intent (`quarantine(id:reason:)`). Quarantining the **history** half of a split workout produces no template notice: a lost workout is a different failure with its own escape hatch (HealthKit recovery + the orphaned-workout banner).

*Where it appears.* On the **watch only**, as a dismissible card at the top of the routine list (`TemplateFailureNoticeRow`, published through `RoutineStore.templateFailureNotices`), which wins over the empty state so a notice for a deleted routine is still shown. That screen is opened before every workout — which is exactly the moment a stale template matters — and the notice persists until the user dismisses it, so no particular screen has to be open at any particular moment. iOS deliberately shows nothing: the watch is the device where the change was accepted and where the value visibly reverts, and it is the only device that knows about **both** terminal causes (a quarantined payload never reaches the iPhone at all). A watch local notification was rejected as well — a new authorization prompt for a rare event, for information that is only actionable next to the routine.

*Where the reason comes from.* The terminal acknowledgment carries a machine outcome and **no human-readable reason**, so the reason is reconstructed on the watch from the outcome plus what the watch already knows: on a rejection, the authoritative base (current by then, since retirement waits for the ack's routine generation to apply) either still carries the routine — `routineChangedOnPhone` — or no longer does — `routineDeleted`; a quarantine is always `couldNotSend`, told as "your change couldn't be sent", never as its internal diagnostic. **Propagating a reason on the wire was rejected**: iOS's rejection reason exists only as a diagnostic `String` on `WatchTemplateTransactionService.Outcome.rejected`, so making it user-facing would mean a rejection-reason enum threaded through `validateMerge`/`applyStructural`, a new acknowledgment key, and a mixed-version story for a build that does not send it — a permanent second wire concern in the merge path, bought for one sentence. Revisit only if the reconstructed reason proves wrong in the field. The notice names the routine (resolved from the base, then the routine anchor, then the payload's `routineName`); naming the individual exercise or set was left out deliberately — it would mean diffing the intent against the base for a message whose action is "open the routine on your iPhone" either way.

*Retention.* Notices live in the sync state file (`templateFailureNotices`, optional so older state stays decodable), survive relaunch, supersede an older notice for the same routine and reason, and are capped at `WatchTemplateFailureNotice.maxRetained` (5) — a nudge, not a log. Dismissal is durable and best effort: a failed write leaves the notice on screen, which is the safe direction.

### Trigger: editing a past workout (iOS)
The template can also change when a user edits a completed workout in History and chooses "Update
template" (see `docs/edit-past-workout.md`). In that case `WorkoutViewModel.saveEditedWorkout` updates
the SwiftData `Routine` and posts `.routineTemplateDidChange`. `RoutinesViewModel` observes this
(`observeRoutineTemplateChanges()`) and calls `fetchRoutines()` → `syncRoutinesToWatch()`, so the
corrected template reaches the watch through the standard `applicationContext` path. No watch-target
code is involved.

### iOS Init Order
`AppDependencies.init` gives `WatchWorkoutIngestionCoordinator` a launch drain BEFORE any `RoutinesViewModel` is constructed. This prevents sending stale routine data to the watch when the iOS app launches with an unprocessed durable-inbox entry (from a prior crash between receive and save):

```
AppDependencies.init → WatchWorkoutIngestionCoordinator.routineAuthorityDidChange()  // recover ready receipts + drain
   → later: RoutinesViewModel.init → fetchRoutines() → syncRoutinesToWatch()
```

## Lightweight Models

- `WatchRoutine` / `WatchExercise` / `WatchSet`: Template data (Codable, Hashable)
- `ActiveWorkoutExercise` / `ActiveWorkoutSet`: In-memory workout state with planned vs actual values
- `CompletedWatchWorkout` / `CompletedWatchExercise` / `CompletedWatchSet`: Completed workout data sent to iOS (Codable wire DTOs; live in `Data/Sync/` on iOS)
- `IncomingWatchWorkout` / `IncomingWatchExercise` / `IncomingWatchSet` (iOS Domain only): the Domain mirror of the completed-workout DTOs. The Data layer maps the wire DTO into these at the boundary so the Domain ingestion service never references a Data type
- `OutgoingSyncEntry` / `OutgoingSyncPayload` / `OutgoingWorkoutPhase` (both targets): a transaction-first durable-queue entry whose payload is either a legacy/no-template completed workout or the generic `TemplateTransactionEnvelope`, plus finalization phase, enqueue time, optional quarantine reason, and optional held terminal acknowledgment
- `RoutineSnapshotHeader` / `WatchRoutineAuthorityState` / `TemplateAckRecord` (both targets): the routine authority wire header, the watch's persisted acceptance state, and a parsed versioned acknowledgment
- `TemplateTransactionKey` / `WorkoutIngestReceipt` (iOS): the `(senderEpoch, routine, sequence)` ordering identity and its phased terminal receipt
- `TemplateTransactionOutcome` / `WatchTemplateTransactionAck` (iOS Domain): the terminal outcome and the acknowledgment value type `WatchSyncServicing` exposes, so Presentation/Domain never touch a wire DTO
- `WorkoutIngestReceipt` (iOS): terminal per-workout receipt (workout id, HK external UUID, phase `readyToAcknowledgeNotRequested`, timestamp)

`WatchExercise.id` is the source `RoutineExercise.id` and remains unchanged through `ActiveWorkoutExercise`, `CompletedWatchExercise`, and `IncomingWatchExercise`. On ingestion, iOS snapshots that value into `WorkoutExercise.routineExerciseId`. This distinguishes repeated uses of the same library exercise in history without adding a new Watch wire field, so old cached routines and mixed app versions retain their existing Codable compatibility.

All models preserve UUIDs from the iOS SwiftData originals for ID-based matching when updating templates.

### Wire schema evolution rule (audit P1.4, fixed 2026-08-13)

**Every field added after v1 to a DTO that is decoded from the wire *or from persistence* must be `Optional` with a `nil` default, in *both* target copies.** A non-optional property with a default value is not a decode-time fallback: synthesized `Decodable` emits `container.decode(...)` for it unconditionally, so an absent key throws `DecodingError.keyNotFound` and the default is never consulted. Only `Optional`-typed properties are synthesized as `decodeIfPresent`. This is compiler-synthesis behavior (`DerivedConformanceCodable.cpp`), unchanged from Swift 4 through 6.3, and no Swift Evolution proposal makes default values participate in decoding. Widening a field to `Optional` does **not** change the wire: a non-nil optional is still encoded (`encodeIfPresent`), so only `nil` omits the key.

The one real drift found by the August 2026 audit across ~4,600 duplicated lines was `CompletedWatchExercise.loadBehaviorRaw` — `String? = nil` on iOS, `String = "resistance"` on the watch since `7812427` (2026-07-12). The watch copy is now `String? = nil`, identical to iOS, and both copies carry the rule as a doc comment.

*Why the watch side was the one that had to widen.* iOS is the receiver and its tolerance for a pre-2026-07-12 payload must not be given up. More importantly, the watch is not only a sender: `CompletedWatchWorkout` is persisted inside `WatchSyncStateStore`'s App-Group state file and its legacy migration blob, so **the watch decodes this type itself**. Blast radius there is not one field — `WatchSyncStateFile` decodes as a whole, so a single undecodable entry quarantines the file as `.corrupt` and starts the outgoing queue empty (`WatchSyncStateStore.swift:117-135`); in `migrateLegacyEntries` an undecodable blob simply never migrates and the workouts are stranded. Apple does not document whether the `transferUserInfo` queue survives an app update, so an old-schema payload reaching a new build cannot be ruled out.

*The one sanctioned exception: a hand-written `init(from:)` (2026-08-13).* `ActiveWorkoutExercise` keeps three fields the rule would otherwise forbid — `loadBehaviorRaw: String = "resistance"`, `isPendingWatchAddition: Bool = false`, `alternatives: [...] = []` — and it *is* decoded from persistence, as `WatchActiveWorkoutCheckpoint.exercises`. Widening them was rejected: it ripples to ~19 read sites, nearly all inside `WatchWorkoutViewModel`, which the audit puts on explicit P3 hold. Instead both copies carry an identical `init(from:)` that reads those three with `decodeIfPresent(...) ?? default`. Three details make this safe rather than a second footgun:

- **It lives in an `extension`.** An `init` in the struct body would suppress the memberwise initializer that every construction site uses.
- **`CodingKeys` and `encode(to:)` stay synthesized** — no hand-written `CodingKeys`, so a newly added property can never be silently dropped from the *encoded* form (which would be a worse hazard than the one being fixed).
- **The decode side is guarded by a test, because the compiler cannot guard it.** A property added later but not decoded in the manual `init` compiles cleanly and then silently never restores. `checkpointExerciseRoundTripPreservesEveryField` has two halves, and the split matters:
  - *Structural* — it pins the encoded key set against an explicit 21-key list and asserts `Mirror(reflecting:).children.count` equals that same count. This is what fails when a property is **added**. Round-trip equality alone does **not**: a new defaulted property left out of both the fixture and the `init` lands on its default on both sides and compares equal. The `Mirror` half additionally covers what a key-set check alone would miss — a new *Optional* property the fixture forgets to populate, which is nil and therefore absent from the encoded keys.
  - *Value* — every field in the fixture is at a non-default value, so a field decoded **incorrectly** (rather than not at all) fails here.

  Both halves were verified to bite: deleting one `decodeIfPresent` fails the value half, and adding an undecoded `var probeAddedLater: Int = 0` fails the structural half while the value half passes. `checkpointDecodesWhenPostV1FieldsAreAbsent` pins the containing checkpoint's key set the same way.

Prefer the `Optional` rule; reach for this only when widening would ripple into held code. The containing `WatchActiveWorkoutCheckpoint` shows where the line falls: it had the identical hazard in `appliedOverloads` and `deferredOverloadSlotIDs` (both non-optional with `[]` defaults, added in `4f82e33` after the 1.1.6 checkpoint shape had already shipped), but those have only **two** read sites, so they were simply widened to Optional and coalesced at their only two read sites in `WatchWorkoutViewModel+Recovery.swift`. Two read sites is not a ripple.

That one mattered more than the exercise-level fix it was found next to. A throw there is not partial: `WatchActiveWorkoutCheckpointStore.load()` swallows it with `try?`, renames the file `.corrupt` and returns nil, so `WatchWorkoutRecoveryPlanner` sees no checkpoint at all and the user's live in-progress workout — exercises, completed values, routine identity, structural baseline — is silently discarded. That is precisely the outcome the checkpoint exists to prevent. `checkpointDecodesWhenPostV1FieldsAreAbsent` (both suites) now decodes a checkpoint with those two keys stripped.

Note the checkpoint's `version: Int` does **not** deliver backward-decodability on its own — decoding never branches on it — and its doc comment now says so. The `appliedOverloads` comment previously asserted that being "defaulted" kept old checkpoints decodable; that claim was load-bearing and false, and is corrected in place.

*Tripwire.* `WatchModelsWireCompatibilityTests` exists in **both** test targets (twin suites, aligned assertions). Each decodes a `CompletedWatchWorkout` containing only the v1 keys and asserts every later addition arrives as `nil`, so any future non-optional wire field fails immediately on the side that added it. The watch suite additionally asserts the sender still emits `loadBehaviorRaw` (the widening did not change the wire) and that an absent value resolves to resistance through `toActiveWorkoutExercise()`; the iOS suite asserts the same fallback at the Data→Domain boundary (`toIncomingWatchExercise`). Verified to bite: reintroducing the drift fails the watch suite with `keyNotFound: Key 'loadBehaviorRaw' ... Path: exercises[0]`.

## UI Feedback
When a template is updated on the watch, a "Template updated" banner appears on the workout summary screen (`WatchWorkoutSummaryView`), driven by `WatchWorkoutViewModel.templateWasUpdated`. That banner reports the accepted intent, not its fate — if the update later turns out to be terminally unappliable, the routine list shows a dismissible notice saying so (see "Telling the user a template update was not applied").
